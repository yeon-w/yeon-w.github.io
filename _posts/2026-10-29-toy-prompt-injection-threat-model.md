프롬프트 인젝션을 공부할 때는 먼저 **누가 어떤 텍스트를 제어하고, 모델이 무엇을 할 수 있는지**를 적는 편이 유용하다. 여기서는 외부 서비스나 실제 사용자 데이터 없이, 합성 문서만 요약하는 연습용 앱을 가정한다. 실제 공격 수행이나 발견 사례를 뜻하지 않는다.

## 가정한 앱과 신뢰 경계

앱의 정상 작업은 로컬 폴더의 문서를 읽고 핵심 내용을 요약하는 것이다. 사용자의 요약 요청과 앱의 동작 규칙은 신뢰된 입력으로 둔다. 읽어 온 문서 본문은 제3자가 작성할 수도 있으므로 **요약할 자료**이지 **앱에 내리는 지시**가 아니다.

| 요소 | 제어 주체 | 다룰 방식 |
| --- | --- | --- |
| 요약 요청과 출력 형식 | 실습 사용자 | 앱의 작업 기준 |
| 합성 문서의 본문 | 실습에서 가정한 외부 작성자 | 인용·요약할 데이터 |
| 요약 결과 | 앱 | 근거가 된 문서와 함께 검토 |

이 연습용 앱에는 외부 전송 기능, 비밀 키, 실행 도구를 넣지 않는다. 범위를 좁히면 관찰한 실패가 무엇인지 구분하기 쉽다.

## 확인할 질문

1. 문서 안에 명령처럼 보이는 문장이 있어도 앱이 이를 **문서의 내용**으로 취급하는가?
2. 요약이 사용자의 요청한 범위와 형식을 유지하는가?
3. 문서에 없는 사실이 결과에 추가되었는가?
4. 어떤 입력에서 결과가 달라졌는지 재현할 수 있는가?

테스트 기록에는 합성 문서, 사용자의 정상 요청, 예상 출력, 실제 출력, 모델·앱 버전을 함께 남긴다. "성공" 기준도 미리 정한다. 예를 들어 출력 형식이 바뀌었는지와 근거 없는 내용이 생겼는지는 서로 다른 실패다.

모델의 응답은 실행 환경과 버전에 따라 바뀔 수 있다. 한 번의 결과를 일반화하지 말고 반복 관찰과 한계를 함께 적는다. 실제 서비스는 해당 서비스의 허가와 정책 없이 시험하지 않는다.
