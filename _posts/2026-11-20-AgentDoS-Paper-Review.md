## 1. 서론: 연구 배경과 문제의식

### 1.1 LLM 에이전트의 자율성과 자원 관리 문제

최근 LLM 기반 에이전트는 사용자의 자연어 요청을 이해하고, 외부 도구를 호출하여 다양한 작업을 자율적으로 수행하는 형태로 발전하고 있다.

예를 들어 사용자가 특정 문서를 분석해 달라고 요청하면 에이전트가 웹사이트에 접근하여 파일을 다운로드하고, 내용을 추출한 뒤 결과를 요약할 수 있다.

이러한 자율성은 사용자의 작업을 효율적으로 처리할 수 있게 해주지만, 동시에 시스템 자원을 과도하게 사용하는 문제로 이어질 수 있다.

기존 소프트웨어는 일반적으로 명확한 실행 흐름에 따라 동작하지만, LLM 에이전트는 자연어 요청에 따라 작업의 종류와 규모가 동적으로 결정된다.

따라서 개발자가 모든 작업의 자원 사용량을 사전에 예측하기 어렵다.

특히 파일 다운로드, 대용량 문서 분석, 대화 기록 저장과 같은 기능에서 메모리와 디스크 사용량을 적절하게 제한하지 않으면 공격자가 정상적인 사용자 요청처럼 보이는 프롬프트만으로 자원을 고갈시킬 수 있다.

### 1.2 DoS 취약점이란?

Denial-of-Service(DoS)는 시스템이 정상적인 사용자에게 서비스를 제공하지 못하도록 만드는 공격이다.

대표적인 원인 중 하나는 Resource Exhaustion, 즉 자원 고갈이다.

시스템이 사용할 수 있는 메모리나 디스크 공간이 소진되면 요청을 처리하지 못하거나 프로세스가 비정상적으로 종료될 수 있다.

LLM 에이전트에서는 이러한 자원 고갈이 자연어 요청으로 유발될 수 있다는 특징이 있다.

예를 들어 파일을 다운로드하고 요약하는 기능이 있는 에이전트에 지나치게 큰 파일을 처리하도록 요청하거나, 동일한 작업을 반복하도록 유도하는 상황을 생각할 수 있다.

이때 에이전트가 파일 크기, 반복 횟수, 누적 자원 사용량을 적절하게 제한하지 않는다면 DoS 취약점으로 이어질 수 있다.

문제는 이러한 요청이 일반적인 사용자 작업과 의미적으로 유사하다는 것이다.

따라서 명백하게 악의적인 명령어나 코드를 탐지하는 방식만으로는 자원 남용을 방지하기 어렵다.

### 1.3 기존 연구 AgentFuzz의 한계

기존 연구인 AgentFuzz는 LLM 기반 에이전트의 Taint-style Vulnerability를 자동으로 탐지하기 위해 Directed Greybox Fuzzing을 활용하였다.

AgentFuzz는 정적 분석으로 위험한 Sink를 탐색하고, LLM을 사용하여 해당 Sink에 도달할 수 있는 자연어 프롬프트를 생성하고 변형한다.

이 방식은 코드 인젝션이나 SQL Injection처럼 특정 위험 함수까지 공격자 입력을 전달해야 하는 취약점에 효과적이다.

그러나 DoS 취약점에는 이를 그대로 적용하기 어렵다.

**첫째, 위험한 함수에 도달하는 것만으로 DoS가 발생하지 않는다.**

예를 들어 파일 다운로드 함수가 실행되더라도 작은 파일만 다운로드하면 시스템에 문제가 발생하지 않을 수 있다.

실제 DoS를 유발하려면 위험한 함수에 도달하는 것뿐 아니라 충분한 자원을 소비하도록 해야 한다.

**둘째, DoS는 여러 요청에 걸쳐 발생할 수 있다.**

AgentFuzz는 기본적으로 개별 프롬프트를 새로운 세션에서 실행하는 방식으로 탐색한다.

그러나 어떤 에이전트는 대화 기록이나 중간 결과를 동일한 세션 내에 계속 저장한다.

이 경우 개별 요청은 정상적으로 처리되더라도 여러 요청이 반복되면 자원이 누적되어 고갈될 수 있다.

**셋째, 자원의 생명주기에 따라 공격 조건이 달라진다.**

어떤 자원은 요청 종료 후 해제되지만, 어떤 자원은 세션 종료 시까지 유지되고, 일부 자원은 세션이 종료된 이후에도 남아 있을 수 있다.

따라서 단일 요청의 실행 경로만 분석하는 방식으로는 자원 고갈 취약점을 충분히 탐지하기 어렵다.

저자들은 이러한 문제를 해결하기 위해 AgentDoS를 제안하였다.

## 2. 문제 정의와 연구 목표

본 논문은 **LLM 기반 에이전트에서 자원의 생명주기를 분석하고, 자연어 프롬프트를 반복적으로 생성·변형하여 자원 고갈에 따른 DoS 취약점을 자동으로 탐지하는 것**을 목표로 한다.

이를 위해 크게 두 가지 문제를 해결해야 한다.

### 2.1 자원의 생명주기를 어떻게 식별할 것인가?

DoS 취약점을 탐지하려면 자원이 언제 할당되고 언제 해제되는지 알아야 한다.

그러나 LLM 에이전트는 여러 프레임워크와 도구를 결합하여 구현되며, 자원 관리 방식도 애플리케이션마다 다르다.

따라서 소스코드를 분석하여 각 자원의 저장 및 해제 과정을 추적할 필요가 있다.

### 2.2 자원 사용량을 극대화하는 자연어 입력을 어떻게 생성할 것인가?

기존 퍼저의 무작위 바이트 변형은 특정 코드 경로를 탐색하는 데 유용할 수 있지만, LLM 에이전트가 수행할 작업의 규모를 효과적으로 증가시키지는 못한다.

예를 들어 다운로드 기능을 실행시키는 프롬프트와 대용량 다운로드 작업을 실행시키는 프롬프트는 기능적으로 유사하지만 자원 소비량은 크게 다를 수 있다.

따라서 목표 기능 호출과 자원 소비 유도라는 두 가지 조건을 동시에 만족하는 프롬프트를 생성해야 한다.

## 3. 핵심 아이디어: AgentDoS

AgentDoS는 자원의 생명주기 분석과 Directed Greybox Fuzzing을 결합한 취약점 탐지 프레임워크이다.

핵심 아이디어는 다음과 같다.

**에이전트의 자원 관리 방식을 먼저 분석하고, 해당 자원의 생명주기에 적합한 프롬프트 실행 전략을 선택하여 실제 자원 고갈을 유발하는 입력을 탐색한다.**

### 3.1 Resource Lifecycle Classification

AgentDoS는 자원을 세 가지 유형으로 구분한다.

**① Short-lived Resource**

단일 요청을 처리하는 동안에만 유지되는 자원이다.

예를 들어 함수 내부에서 생성한 임시 데이터가 요청 종료 후 해제되는 경우이다.

이러한 자원은 여러 요청에 걸쳐 누적되지 않으므로 하나의 요청에서 상당한 양의 자원을 소비하도록 해야 한다.

**② Long-lived Resource**

하나의 대화 세션 동안 유지되며 세션 종료 시 해제되는 자원이다.

대표적으로 대화 기록이나 세션에 종속된 캐시가 있다.

이러한 자원은 동일한 세션에서 여러 요청을 반복하여 누적시키는 방식으로 고갈될 수 있다.

**③ Full-lifecycle Resource**

대화 세션이 종료된 이후에도 유지되는 자원이다.

예를 들어 다운로드한 파일이 삭제되지 않고 디스크에 계속 저장되는 경우이다.

이러한 자원은 여러 세션에 걸쳐 누적될 수 있으므로 세션을 새로 시작하더라도 시스템의 자원 사용량이 증가할 수 있다.

이처럼 자원 유형에 따라 공격 조건이 달라진다는 점이 AgentDoS의 핵심적인 문제의식이다.

### 3.2 Resource-aware Directed Fuzzing

AgentFuzz는 Seed가 목표 Sink에 얼마나 가까이 도달했는지를 주요 피드백으로 사용하였다.

반면 AgentDoS는 다음 두 가지 요소를 함께 고려한다.

- **Functionality Score:** 프롬프트가 목표 기능을 얼마나 효과적으로 실행하는가?
- **Resource Consumed Score:** 프롬프트 실행으로 실제 시스템 자원이 얼마나 소비되는가?

이 두 요소를 활용하면 목표 함수를 실행할 뿐 아니라 실제 자원 소비량이 높은 Seed를 우선적으로 선택할 수 있다.

이는 단순히 코드 실행 경로에 집중하는 퍼징에서 벗어나 시스템의 실행 상태와 자원 소비 결과까지 고려한다는 의미가 있다.

## 4. 방법론 및 시스템 구성

AgentDoS는 크게 두 개의 단계로 구성된다.

### 4.1 Vulnerable Operator Modeling

첫 번째 단계는 자원 고갈을 발생시킬 가능성이 있는 연산을 탐색하고 분석하는 것이다.

**① Vulnerability Candidates Locating**

AgentDoS는 CodeQL 기반 정적 분석을 사용하여 메모리 또는 디스크 자원 사용과 관련된 연산을 찾는다.

주요 분석 대상에는 리스트나 딕셔너리와 같은 자료구조에 데이터를 저장하는 연산, 메모리를 많이 소비할 수 있는 파싱 연산, 디스크 쓰기 연산 등이 포함된다.

이러한 연산을 잠재적인 Sink로 간주한다.

**② Resource Lifecycle Identification**

다음으로 자원 사용 연산이 실행된 이후 해당 자원이 언제 해제되는지 분석한다.

예를 들어 함수가 종료된 뒤 더 이상 참조되지 않는 데이터라면 Short-lived Resource로 분류한다.

반면 세션 객체에 저장된 데이터라면 세션 종료 시점의 정리 로직을 확인한다.

세션 종료와 함께 해제되면 Long-lived Resource, 세션 종료 후에도 유지되면 Full-lifecycle Resource로 분류한다.

**③ Exploitability Assessment**

모든 자원 사용 연산이 DoS 취약점으로 이어지는 것은 아니다.

따라서 AgentDoS는 사용자 입력이 해당 연산에 영향을 줄 수 있는지, 데이터 크기나 반복 횟수에 대한 명시적인 제한이 존재하는지를 확인한다.

이를 위해 함수 내부의 Taint Analysis와 조건문 분석을 수행한다.

사용자 입력으로 제어할 수 없거나 명확한 크기 제한이 적용된 연산은 이후 퍼징 대상에서 제외한다.

이 과정을 통해 실제 취약점이 발생할 가능성이 있는 후보에 분석 자원을 집중한다.

### 4.2 Dynamic Fuzzing

두 번째 단계는 선택한 후보를 대상으로 실제 프롬프트를 생성하고 변형하는 과정이다.

#### ① Seed Generation

AgentDoS는 먼저 분석 대상 에이전트의 System Prompt와 함수 호출 경로를 추출한다.

이때 System Prompt는 에이전트가 사용할 수 있는 도구와 기능을 설명하므로 어떤 프롬프트가 특정 기능을 실행시킬 수 있는지 추론하는 데 중요한 정보가 된다.

AgentDoS는 이러한 정보를 LLM에 제공하여 목표 기능을 실행하도록 유도하는 초기 Seed를 생성한다.

#### ② Seed Scheduling

생성된 Seed는 실제 실행 결과를 바탕으로 평가된다.

AgentDoS의 Seed Selection Score는 다음과 같은 구조를 갖는다.

`Seed Score = α × Functionality Score + β × Resource Consumed Score − Penalty`

Functionality Score는 목표 코드까지의 거리와 프롬프트의 의미적 적합성을 고려한다.

Resource Consumed Score는 실제 메모리 또는 디스크 사용량을 바탕으로 계산한다.

다만 자원의 생명주기에 따라 측정 기준이 달라진다.

Short-lived Resource에서는 요청 실행 중 최대 자원 사용량을 측정한다.

반면 Long-lived 및 Full-lifecycle Resource에서는 요청 처리 후에도 남아 있는 자원 사용량을 평가한다.

이를 통해 단발적인 자원 사용과 누적되는 자원 사용을 구분할 수 있다.

#### ③ Seed Mutation

선택된 Seed를 변형하기 위해 두 종류의 Mutator를 사용한다.

**Explorer**

목표 자원 사용 연산에 도달하지 못한 프롬프트를 수정한다.

LLM에 목표 함수의 호출 경로, System Prompt, 이전 실행 결과를 제공하고 목표 기능이 실행되도록 자연어 표현을 조정한다.

**Exploiter**

목표 기능이 실행되었지만 자원 사용량이 충분하지 않은 경우 사용한다.

이 단계에서는 기능 자체를 변경하기보다 해당 기능의 자원 소비를 증가시키는 방향으로 프롬프트를 변형한다.

즉, Explorer가 목표 기능을 실행하도록 만드는 역할이라면 Exploiter는 실제 자원 고갈을 유도할 수 있는 입력을 탐색하는 역할이다.

#### ④ Lifecycle-aware Prompt Dispatch

AgentDoS의 또 다른 특징은 자원 생명주기에 맞게 프롬프트 실행 방식을 조정한다는 것이다.

Short-lived Resource는 새로운 세션에서 개별 프롬프트를 실행하며 자원 고갈을 확인한다.

Long-lived Resource는 동일한 세션에서 프롬프트를 반복 실행하여 누적되는 자원 사용량을 관찰한다.

Full-lifecycle Resource는 여러 세션에 걸쳐 자원이 유지되는 특성을 활용하여 자원 소비가 누적되는지 확인한다.

이 과정에서 시스템의 자원 사용량과 서비스 응답 상태를 지속적으로 관찰하며, 서비스가 응답하지 않는 상황이 확인되면 DoS 후보로 기록하고 검증한다.

---

## 5. 실험 및 평가

저자들은 20개의 오픈소스 LLM 에이전트를 대상으로 AgentDoS를 평가하였다.

분석 대상에는 AutoGPT, Langflow, Dify, RAGFlow 등 널리 사용되는 에이전트 프로젝트가 포함되었다.

### 5.1 취약점 탐지 결과

| 평가 항목 | 결과 |
|---|---:|
| 평가 대상 에이전트 | 20개 |
| 자원 생명주기 식별 정확도 | 95.2% |
| 발견한 새로운 DoS 취약점 | 36개 |
| 취약점이 발견된 에이전트 | 16개 |
| 부여된 CVE | 15개 |
| Precision | 100% |
| 비교용 정답 집합에 대한 Recall | 94.7% |
| 전체 퍼징 CPU 시간 | 119.08시간 |
| 에이전트당 평균 퍼징 CPU 시간 | 5.95시간 |

AgentDoS는 총 36개의 새로운 DoS 취약점을 발견하였으며, 수동 검증에서 모두 실제 취약점으로 확인되었다.

이 결과는 자원 사용 연산과 프롬프트의 실행 결과를 함께 분석하면 기존의 코드 중심 취약점 탐지 방식이 놓칠 수 있는 가용성 문제를 발견할 수 있음을 보여준다.

### 5.2 AgentFuzz와의 비교

저자들은 AgentDoS와 AgentFuzz를 동일한 자원 고갈 취약점 탐지 환경에서 비교하였다.

| 평가 항목 | AgentFuzz | AgentDoS |
|---|---:|---:|
| True Positive | 3 | 36 |
| False Positive | 0 | 0 |
| False Negative | 35 | 2 |
| Precision | 100% | 100% |
| Recall | 7.9% | 94.7% |

AgentDoS는 AgentFuzz보다 훨씬 많은 DoS 취약점을 탐지하였다.

그 이유는 크게 두 가지로 설명할 수 있다.

첫째, AgentFuzz는 개별 프롬프트를 새로운 세션에서 실행하므로 동일한 세션 내에 자원이 누적되는 취약점을 발견하기 어렵다.

둘째, AgentFuzz는 특정 Sink에 도달하는 데 초점을 맞추기 때문에 해당 함수에서 충분한 자원 소비가 발생하는지까지 최적화하지 않는다.

반면 AgentDoS는 자원 소비량을 Seed의 평가 기준으로 사용하고 자원의 생명주기에 따라 프롬프트 실행 전략을 변경한다.

다만 이 비교는 **DoS 취약점 38개로 구성된 평가 집합에서 수행한 결과**이다.

따라서 AgentDoS가 모든 취약점 유형에서 AgentFuzz보다 우수하다는 의미가 아니라, 자원 고갈 DoS라는 특정 문제에 적합하게 설계되었음을 보여주는 결과로 이해해야 한다.

### 5.3 Ablation Study

저자들은 각 구성 요소가 탐지 성능에 미치는 영향을 평가하였다.

| 실험 구성 | 탐지 취약점 | Recall |
|---|---:|---:|
| 전체 AgentDoS | 36 | 94.7% |
| Seed Generation 제거 | 31 | 81.6% |
| Seed Scheduling 제거 | 25 | 65.7% |
| Seed Mutation 제거 | 16 | 42.1% |

가장 큰 성능 저하는 Seed Mutation을 제거했을 때 발생하였다.

이는 초기 프롬프트만으로는 자원 고갈에 필요한 실행 조건을 만족하기 어렵고, 실제 실행 피드백을 활용하여 입력을 반복적으로 수정하는 과정이 중요하다는 점을 보여준다.

특히 DoS 탐지에서는 목표 기능을 실행하는 것뿐 아니라 자원 소비를 증가시키는 방향으로 입력을 최적화해야 하므로 Seed Mutation의 역할이 크다고 볼 수 있다.

## 6. 한계점 및 아쉬운 점

### 6.1 소스코드 접근이 필요함

AgentDoS는 CodeQL 기반 정적 분석으로 자원 사용 연산과 생명주기를 식별한다.

따라서 소스코드를 확인할 수 없는 상용 에이전트에 그대로 적용하기 어렵다.

이러한 환경에서는 응답 시간이나 요청 실패 여부와 같은 외부 관찰 정보만으로 자원 소비를 추정해야 한다.

### 6.2 메모리 및 디스크 중심의 탐지 범위

논문에서는 주로 메모리와 디스크 자원 고갈을 대상으로 한다.

그러나 실제 에이전트에서는 CPU 사용량, 외부 API 호출 횟수, 네트워크 연결 수, LLM 토큰 사용량 등도 가용성에 영향을 줄 수 있다.

따라서 다양한 자원 유형을 함께 고려하도록 확장할 필요가 있다.

### 6.3 자원 고갈 판단 기준의 환경 의존성

DoS 취약점은 시스템의 하드웨어 사양과 자원 제한 정책에 영향을 받는다.

동일한 프롬프트라도 메모리 용량이 큰 환경에서는 문제가 발생하지 않을 수 있으며, 자원이 제한된 환경에서는 서비스 장애가 발생할 수 있다.

따라서 탐지된 취약점이 다양한 실행 환경에서도 재현되는지 확인하는 과정이 중요하다.

### 6.4 퍼징 비용과 확장성

AgentDoS는 전체 실험에서 약 119 CPU 시간을 사용하였다.

또한 논문에서는 에이전트당 평균 약 932만 개의 LLM 토큰을 소비했다고 보고하였다.

이는 복잡한 자원 사용 동작을 탐색하기 위해 상당한 계산 비용과 LLM 호출 비용이 발생할 수 있음을 의미한다.

따라서 실제 대규모 보안 테스트에 적용하려면 Seed 선택 효율성과 자원 사용량 예측 정확도를 개선할 필요가 있다.

## 7. 내가 생각하는 후속 연구 방향

### 7.1 다양한 자원 유형으로 탐지 범위 확장

가장 먼저 확장해 보고 싶은 방향은 메모리와 디스크뿐 아니라 CPU, 네트워크, 외부 API 호출량 등을 고려하는 것이다.

특히 LLM 에이전트는 여러 도구를 연속적으로 실행하므로 단일 자원의 고갈뿐 아니라 여러 자원 사이의 상호작용으로 서비스 장애가 발생할 수 있다.

따라서 개별 자원의 사용량과 전체 작업 처리 능력을 함께 측정하는 방식으로 확장할 수 있을 것이다.

### 7.2 Stateful Agent Fuzzing

AgentDoS는 자원의 생명주기를 고려한다는 점에서 기존 AgentFuzz보다 상태 정보의 활용 범위를 넓혔다.

그러나 실제 에이전트는 대화 기록 외에도 사용자별 설정, 작업 큐, 도구 실행 상태, 공유 자원 점유 정보 등 다양한 상태를 유지한다.

따라서 여러 사용자와 에이전트가 동시에 작업을 수행하는 환경에서 상태 변화에 따라 발생하는 가용성 문제를 탐색할 수 있을 것이다.

특히 단일 프롬프트의 자원 소비가 크지 않더라도 여러 작업이 특정 순서로 실행될 때 교착상태나 무한 재시도가 발생하는 상황을 탐지하는 방향이 의미 있다고 생각한다.

### 7.3 자원 사용량 기반 보안 불변조건 검증

또 다른 방향은 자원 사용량을 단순히 증가시키는 것을 넘어 시스템이 유지해야 하는 가용성 조건을 정의하는 것이다.

예를 들어 사용자별 자원 사용량이 정해진 할당량을 초과하지 않아야 한다는 조건이나, 작업이 실패한 이후에도 자원이 정상적으로 반환되어야 한다는 조건을 정의할 수 있다.

이후 정상적인 작업 요청과 취소, 재시도, 세션 종료 등의 동작을 조합하여 해당 조건이 위반되는지 확인할 수 있다.

이는 퍼징과 상태 기반 검증을 결합하여 단순한 자원 고갈뿐 아니라 자원 관리 로직의 결함을 탐지하는 방향으로 확장할 수 있을 것이다.

## 8. 결론 및 느낀 점

이 논문을 읽으며 가장 인상적이었던 부분은 기존 AgentFuzz의 접근을 단순히 다른 취약점에 적용하는 데 그치지 않고, DoS 취약점의 특성에 맞게 퍼징의 목표와 실행 방식을 재설계했다는 것이다.

AgentFuzz에서 중요한 것은 특정 Sink에 도달하는 것이었다. 그러나 AgentDoS에서는 Sink에 도달한 이후 실제로 얼마나 많은 자원을 소비하는지, 해당 자원이 얼마나 오래 유지되는지까지 고려해야 한다.

특히 자원을 Short-lived, Long-lived, Full-lifecycle로 구분한 접근이 흥미로웠다.

같은 메모리나 디스크를 사용하는 작업이더라도 자원이 해제되는 시점에 따라 취약점 발생 조건이 달라질 수 있다는 점을 확인할 수 있었다.

또한 기존 Seed Scheduling에 Resource Consumed Score를 추가한 점도 의미 있다고 생각한다.

퍼징의 목표가 코드 커버리지나 특정 코드 위치에 도달하는 것에만 한정되지 않고, 실제 시스템에서 관찰할 수 있는 자원 사용량과 서비스 상태로 확장될 수 있다는 사실을 보여주기 때문이다.

다만 이 연구는 주로 메모리와 디스크 자원 고갈을 대상으로 하므로, 실제 에이전트 운영 환경에서 발생하는 복잡한 가용성 문제를 모두 다루지는 못한다.

예를 들어 여러 에이전트가 공유 자원을 점유하거나 작업이 반복적으로 재시도되는 상황에서는 단순한 자원 사용량 증가 외에도 상태 전이와 작업 간 의존관계를 분석할 필요가 있을 것이다.

결과적으로 AgentDoS는 **LLM 에이전트의 자원 생명주기와 실제 자원 소비량을 Directed Greybox Fuzzing에 통합하여, 기존 취약점 탐지 기법이 놓치기 쉬운 DoS 취약점을 자동으로 발견한 연구**라고 정리할 수 있다.

이번 논문을 통해 취약점의 특성에 따라 퍼징의 목표 함수와 실행 전략을 다르게 설계해야 한다는 점을 배울 수 있었다.
