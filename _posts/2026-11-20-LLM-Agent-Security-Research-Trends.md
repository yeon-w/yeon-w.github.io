# [논문 트렌드 분석] LLM 에이전트 보안 연구의 발전: 취약점 탐지에서 자원 관리와 최소 권한 제어

## 1. 연구 주제 및 논문 선정

### 1.1 연구 주제

**LLM 기반 에이전트의 보안 취약점 탐지 기술과 실행 행동 검증 연구의 발전**

최근 LLM 기반 에이전트는 단순히 자연어 질문에 답변하는 것을 넘어, 외부 도구를 호출하고 코드를 실행하며 실제 시스템을 조작하는 형태로 발전하고 있다.

이러한 변화는 새로운 보안 문제를 발생시킨다. 기존 LLM에서는 공격자의 입력으로 모델의 응답이 왜곡되는 문제가 주로 논의되었다면, 에이전트 환경에서는 모델의 잘못된 판단이 실제 시스템에서 위험한 함수 실행이나 권한 남용으로 이어질 수 있다.

특히 에이전트는 자연어 요청에 따라 실행할 도구와 인자를 동적으로 결정한다. 따라서 기존 소프트웨어의 정적 분석이나 퍼징 기법만으로는 취약점이 발생하는 조건을 충분히 탐색하기 어렵다.

본 분석에서는 이러한 문제를 해결하기 위해 등장한 AgentFuzz를 중심으로, 이전 연구에서 어떤 한계가 존재했고 이를 어떻게 해결했는지, 이후 연구가 어떤 방향으로 확장되었는지 살펴보고자 한다.

### 1.2 분석 대상 논문

| 구분 | 논문 | 학회 | 연도 |
|---|---|---|---|
| 선행 ① | Directed Greybox Fuzzing (AFLGo) | ACM CCS | 2017 |
| 선행 ② | Demystifying RCE Vulnerabilities in LLM-Integrated Apps (LLMSmith) | ACM CCS | 2024 |
| **중심** | **Make Agent Defeat Agent (AgentFuzz)** | **USENIX Security** | **2025** |
| 후속 ① | Autonomy Comes with Costs (AgentDoS) | USENIX Security | 2026 |
| 확장 ② | SkillScope: Toward Fine-Grained Least-Privilege Enforcement for Agent Skills | ACM CCS | 2026 |

두 선행 논문은 AgentFuzz가 해결하려는 문제를 서로 다른 관점에서 설명한다.

AFLGo는 특정 목표 코드에 효율적으로 도달하기 위한 퍼징 기법을 제안한 연구이고, LLMSmith는 LLM 기반 애플리케이션에서 발생하는 실제 코드 실행 취약점을 분석한 연구이다.

AgentFuzz는 두 연구의 문제의식을 연결하여 LLM 에이전트에 특화된 자동 취약점 탐지 기법을 제안하였다.

이후 AgentDoS는 AgentFuzz의 퍼징 접근을 자원 고갈 DoS 취약점으로 확장했으며, SkillScope는 에이전트가 수행하는 행동의 필요성과 권한을 검증하는 새로운 보안 문제를 다룬다.

단, SkillScope는 AgentFuzz의 알고리즘을 직접 개선한 후속작이라기보다, LLM 에이전트의 실행 행동 보안이라는 더 넓은 문제로 연구 범위를 확장한 관련 연구이다.

## 2. 연구 배경: 왜 LLM 에이전트 보안이 중요한가?

### 2.1 LLM에서 LLM 에이전트로의 변화

일반적인 LLM과 LLM 에이전트의 가장 큰 차이는 외부 시스템에 실제 행동을 수행할 수 있는지 여부이다.

일반적인 LLM은 사용자의 질문에 답변을 생성하지만, LLM 에이전트는 요청에 따라 파일을 읽고, 코드를 실행하고, 데이터베이스에 접근하는 등 외부 도구를 사용할 수 있다.

예를 들어 사용자가 데이터베이스 분석을 요청하면 에이전트는 다음과 같이 동작할 수 있다.

1. 사용자 요청을 LLM에 전달한다.
2. LLM이 필요한 도구와 실행할 작업을 결정한다.
3. 에이전트가 선택된 도구에 인자를 전달한다.
4. 도구가 실제 시스템에서 작업을 수행한다.
5. 실행 결과를 사용자에게 반환한다.

이러한 구조에서는 LLM이 생성한 출력이 실제 시스템 동작에 영향을 미친다.

문제는 LLM의 출력이 항상 안전하거나 신뢰할 수 있는 것은 아니라는 점이다. 공격자가 악의적인 자연어 요청을 전달하면 LLM이 위험한 도구를 선택하거나 검증되지 않은 인자를 전달하도록 유도할 수 있다.

따라서 기존의 프롬프트 인젝션 문제가 실제 소프트웨어 취약점과 결합할 수 있다.

### 2.2 기존 소프트웨어 보안과 달라진 공격 표면

전통적인 소프트웨어에서는 사용자 입력이 특정 함수로 전달되는 경로를 정적 분석이나 동적 분석으로 추적할 수 있다.

그러나 LLM 에이전트에서는 사용자 입력과 실제 실행 함수 사이에 LLM의 자연어 해석 및 도구 선택 과정이 존재한다.

즉, 동일한 프로그램이라도 사용자 프롬프트의 의미에 따라 완전히 다른 실행 경로가 선택될 수 있다.

이러한 특성은 두 가지 문제를 만든다.

첫째, 정적 분석으로 위험한 함수의 존재를 확인하더라도 실제로 해당 함수를 호출하는 프롬프트를 찾기 어렵다.

둘째, 단순히 입력의 바이트를 변경하는 퍼징은 자연어의 의미를 훼손하여 원하는 기능을 실행하지 못할 수 있다.

결과적으로 LLM 에이전트의 보안을 검증하려면 **프로그램의 코드 구조와 자연어 입력의 의미를 함께 고려하는 방법**이 필요하다.

## 3. 선행 연구 ①: Directed Greybox Fuzzing (2017)

### 3.1 기존 퍼징 기법의 문제

Directed Greybox Fuzzing은 2017년 ACM CCS에서 발표된 연구로, 특정 목표 코드에 도달하도록 퍼징을 유도하는 AFLGo를 제안하였다.

기존 Coverage-guided Greybox Fuzzing은 프로그램의 다양한 실행 경로를 탐색하고 코드 커버리지를 높이는 데 집중하였다.

대표적인 퍼저인 AFL은 새로운 실행 경로를 발견하면 해당 입력을 저장하고 다시 변형하는 방식으로 동작한다.

그러나 실제 보안 테스트에서는 모든 코드 경로를 탐색하는 것보다 특정한 코드 위치에 도달하는 것이 중요한 경우가 있다.

예를 들어 보안 패치가 적용된 부분을 검사하거나, 정적 분석에서 발견한 잠재적 취약점을 실제로 재현해야 하는 경우가 있다.

이러한 상황에서 기존 퍼저는 목표와 관련 없는 코드도 계속 탐색하기 때문에 시간과 계산 자원을 낭비할 수 있다.

### 3.2 AFLGo의 핵심 아이디어

AFLGo는 프로그램의 Call Graph와 Control Flow Graph를 분석하여 각 코드 위치에서 목표 지점까지의 거리를 계산한다.

이후 실제 실행 결과를 바탕으로 목표 코드에 가까운 Seed에 더 많은 퍼징 자원을 할당한다.

또한 Simulated Annealing 기반 Power Scheduling을 사용하여 Exploration과 Exploitation 사이의 균형을 조절한다.

퍼징 초기에는 다양한 경로를 탐색하지만, 시간이 지날수록 목표에 가까운 Seed에 집중하는 방식이다.

이를 통해 기존 Greybox Fuzzing의 실행 속도를 유지하면서도 목표 코드에 효율적으로 접근할 수 있다.

### 3.3 주요 평가 결과

AFLGo는 실제 오픈소스 프로그램을 대상으로 수행한 실험에서 총 39개의 버그를 발견하였으며, 17개의 CVE가 부여되었다.

또한 Heartbleed 취약점 재현 실험에서는 평균 약 19분 만에 취약점을 재현하여 목표 지향적 퍼징의 효과를 보여주었다.

### 3.4 한계와 다음 연구로의 연결

AFLGo는 특정 목표 코드에 도달하는 문제를 효과적으로 해결했지만, 두 가지 한계가 있다.

첫째, 목표 지점을 사전에 지정해야 한다.

둘째, 코드상으로 목표와 가깝다는 사실이 실제 실행 가능성을 보장하지 않는다.

특히 LLM 에이전트에서는 자연어의 의미에 따라 실행할 도구가 달라지기 때문에 코드상의 거리만으로는 입력이 목표 함수에 도달할 가능성을 정확하게 평가하기 어렵다.

또한 기존 AFLGo의 바이트 기반 입력 변형을 자연어 프롬프트에 그대로 적용하면 프롬프트의 의미가 손상될 수 있다.

따라서 LLM 에이전트에 Directed Greybox Fuzzing을 적용하려면 목표 코드와의 거리뿐 아니라 자연어 의미를 고려하는 새로운 접근이 필요하다.

**AFLGo는 AgentFuzz에 목표 지향적 퍼징이라는 기술적 기반을 제공한 연구라고 볼 수 있다.**

## 4. 선행 연구 ②: LLMSmith (2024)

### 4.1 LLM 애플리케이션에서 발생하는 RCE 문제

LLMSmith는 2024년 ACM CCS에서 발표된 연구로, LLM 기반 프레임워크와 애플리케이션에서 발생하는 Remote Code Execution(RCE) 취약점을 탐지하고 검증하는 방법을 제안하였다.

LLM이 외부 코드 실행 도구와 결합되면 공격자가 자연어 요청만으로 시스템에서 임의의 코드를 실행하도록 유도할 수 있다.

예를 들어 애플리케이션이 LLM이 생성한 코드를 별도의 검증 없이 `exec()`와 같은 함수에 전달한다면 RCE가 발생할 수 있다.

문제는 이러한 취약점이 애플리케이션의 코드뿐 아니라 프레임워크 내부의 API와 연결되어 있다는 점이다.

따라서 단순한 프롬프트 분석만으로는 취약점의 실제 원인을 충분히 파악하기 어렵다.

### 4.2 LLMSmith의 핵심 아이디어

LLMSmith는 정적 분석과 실제 공격 검증을 결합하였다.

첫 번째 단계에서는 프레임워크의 소스코드를 분석하여 사용자 입력 API에서 위험한 코드 실행 함수까지 이어지는 Call Chain을 추출한다.

두 번째 단계에서는 해당 API를 사용하는 실제 애플리케이션을 수집한다.

세 번째 단계에서는 프롬프트 기반 테스트를 수행하여 실제로 위험한 코드가 실행되는지 확인한다.

이를 통해 잠재적으로 위험한 함수가 존재한다는 사실뿐 아니라 실제 애플리케이션에서 공격 가능한지까지 분석하였다.

### 4.3 주요 평가 결과

LLMSmith는 11개의 LLM 기반 프레임워크에서 총 20개의 취약점을 발견하였다.

이 중 19개는 RCE 취약점이었으며, 나머지 1개는 임의 파일 읽기 및 쓰기 취약점이었다.

또한 실제 애플리케이션 51개를 테스트한 결과 17개 애플리케이션에서 공격에 성공하였다.

이는 LLM이 외부 시스템 기능을 사용할 수 있게 되면서 기존 소프트웨어 취약점이 새로운 방식으로 악용될 수 있음을 보여준다.

### 4.4 한계와 다음 연구로의 연결

LLMSmith의 가장 큰 한계는 정적 분석으로 발견한 잠재적 취약점과 실제 공격 가능한 취약점 사이에 차이가 있다는 것이다.

Source에서 Sink까지 호출 경로가 존재하더라도 실제 실행 중 조건문이나 입력 검증 때문에 해당 경로에 도달하지 못할 수 있다.

또한 실제 공격 검증 과정에서 사전에 준비된 프롬프트를 활용하거나 사람의 개입이 필요한 경우가 존재한다.

따라서 잠재적인 취약점을 자동으로 재현하는 데 한계가 있다.

이러한 문제는 새로운 연구 질문으로 이어진다.

**정적 분석으로 발견한 위험한 함수까지 실제로 도달할 수 있는 자연어 프롬프트를 자동으로 생성하고, 그 결과를 검증할 수는 없을까?**

이 질문이 AgentFuzz의 핵심 문제의식과 직접적으로 연결된다.

## 5. 중심 논문: AgentFuzz (2025)

### 5.1 AgentFuzz가 해결하려는 문제

AgentFuzz는 2025년 USENIX Security에서 발표된 연구로, LLM 기반 에이전트의 Taint-style Vulnerability를 자동으로 탐지하는 Directed Greybox Fuzzing 프레임워크이다.

Taint-style Vulnerability는 신뢰할 수 없는 외부 입력이 충분한 검증 없이 보안상 민감한 함수에 전달되어 발생하는 취약점을 의미한다.

예를 들어 사용자 입력이 LLM을 통해 코드 실행 함수나 SQL 실행 함수로 전달되는 경우가 해당한다.

AgentFuzz 이전 연구에서는 두 가지 기술적 기반이 존재했다.

AFLGo는 특정 코드에 도달하는 효율적인 퍼징 방법을 제시했고, LLMSmith는 LLM 애플리케이션 내부에 존재하는 위험한 호출 경로를 분석하였다.

그러나 두 연구만으로는 LLM 에이전트의 취약점을 완전히 자동화하여 탐지하기 어려웠다.

기존 Directed Fuzzing은 자연어 입력을 효과적으로 생성하지 못했고, 기존 정적 분석은 위험한 경로가 실제로 실행 가능한지 정확하게 판단하기 어려웠기 때문이다.

AgentFuzz는 이러한 문제를 해결하기 위해 **자연어 의미를 이해하는 LLM과 실제 코드 실행 정보를 활용하는 퍼징 기법을 결합하였다.**

### 5.2 핵심 연구 문제

AgentFuzz는 세 가지 문제를 해결하고자 하였다.

**첫째, 목표 기능을 실행하는 자연어 Seed를 어떻게 생성할 것인가?**

LLM 에이전트는 자연어의 의미에 따라 실행할 기능을 결정한다.

따라서 단순한 무작위 입력 대신 목표 함수의 기능을 정확하게 호출할 수 있는 프롬프트가 필요하다.

**둘째, 어떤 Seed가 목표 Sink에 도달할 가능성이 높은지 어떻게 판단할 것인가?**

기존 Directed Greybox Fuzzing은 목표 코드까지의 거리를 기준으로 입력을 평가하였다.

하지만 LLM 에이전트에서는 동일한 코드 거리의 Seed라도 자연어 의미에 따라 실제 목표 도구 호출 가능성이 달라질 수 있다.

따라서 코드상의 거리와 의미적 유사성을 함께 고려해야 한다.

**셋째, 실제 취약점을 발생시키도록 Seed를 어떻게 변형할 것인가?**

목표 함수를 호출하더라도 함수 내부의 조건문을 만족하지 못하면 취약점이 발생하지 않을 수 있다.

따라서 자연어 프롬프트를 변형하여 목표 기능을 실행할 뿐 아니라 코드 내부의 제약조건까지 만족하도록 만들어야 한다.

### 5.3 핵심 아이디어 및 방법론

AgentFuzz는 크게 세 가지 단계로 구성된다.

#### ① LLM-assisted Seed Generation

첫 번째 단계는 목표 기능을 실행할 수 있는 자연어 Seed를 생성하는 것이다.

AgentFuzz는 먼저 CodeQL 기반 정적 분석으로 보안상 민감한 Sink를 찾고, 해당 함수에 도달할 수 있는 호출 경로를 추출한다.

이후 함수명과 클래스명에 포함된 의미 정보를 LLM에 제공한다.

예를 들어 특정 함수가 데이터베이스 검색과 관련된 기능이라면 LLM은 해당 기능을 실행할 수 있는 자연어 요청을 생성한다.

이 방식은 무작위 프롬프트를 생성하는 대신 프로그램의 기능을 이해한 후 그 기능을 실행하도록 요청한다는 점에서 기존 퍼징과 차이가 있다.

#### ② Feedback-driven Seed Scheduling

두 번째 단계는 생성된 Seed를 실제 실행한 후 어떤 Seed를 우선적으로 변형할지 결정하는 것이다.

AgentFuzz는 다음 세 가지 정보를 활용한다.

- **Semantic Score:** 프롬프트의 의미가 목표 기능과 얼마나 유사한가?
- **Distance Score:** 실제 실행 경로가 목표 Sink에 얼마나 가까운가?
- **Penalty Score:** 특정 Seed나 호출 경로를 과도하게 반복 탐색하고 있는가?

이러한 정보를 종합하여 유망한 Seed에 더 높은 우선순위를 부여한다.

특히 Semantic Score는 기존 AFLGo와 구분되는 중요한 요소이다.

기존 방식에서는 코드상의 거리가 같으면 두 Seed의 품질을 구분하기 어려웠지만, AgentFuzz는 자연어 의미를 활용하여 목표 기능을 실행할 가능성이 높은 입력을 선택할 수 있다.

#### ③ Sink-guided Seed Mutation

세 번째 단계는 선택된 Seed를 변형하여 실제 취약점 발생 조건을 만족시키는 것이다.

AgentFuzz는 두 종류의 Mutator를 사용한다.

**Functionality Mutator**는 프롬프트가 목표 기능을 실행하지 못하는 경우 사용한다.

LLM에 실행 결과와 목표 함수 정보를 제공하여 프롬프트의 의미를 수정한다.

반면 **Argument Mutator**는 목표 함수가 실행되었지만 내부 조건문을 만족하지 못하는 경우 사용한다.

이 과정에서는 Concolic Execution과 제약조건 해결 기법을 사용하여 목표 코드 경로에 도달하는 데 필요한 인자 조건을 구한다.

이후 해당 조건을 만족하도록 자연어 프롬프트의 일부를 변형한다.

즉, Functionality Mutator는 목표 도구를 실행하도록 만드는 역할이고, Argument Mutator는 해당 도구 내부의 제약조건을 만족하도록 만드는 역할이다.

AgentFuzz는 이러한 과정을 반복하며 실제 취약점이 발생하는 입력을 자동으로 탐색한다.

### 5.4 실험 및 평가 결과

저자들은 AgentFuzz를 20개의 오픈소스 LLM 에이전트에 적용하였다.

그 결과 다음과 같은 성과를 얻었다.

| 평가 항목 | 결과 |
|---|---:|
| 평가 대상 에이전트 | 20개 |
| 발견한 새로운 취약점 | 34개 |
| 취약점이 발견된 에이전트 | 14개 |
| 당시 부여된 CVE | 23개 |
| 검증된 탐지 결과의 Precision | 100% |
| 비교 평가 집합에서의 Recall | 97.14% |

특히 발견한 34개의 취약점은 모두 수동으로 검증되어 실제 악용 가능한 것으로 확인되었다.

기존 LLMSmith와 비교한 실험에서는 다음과 같은 차이가 나타났다.

| 평가 지표 | LLMSmith | AgentFuzz |
|---|---:|---:|
| True Positive | 10 | 34 |
| False Positive | 332 | 0 |
| Precision | 2.92% | 100% |
| Recall | 28.57% | 97.14% |

이 결과는 AgentFuzz가 단순한 정적 분석보다 실제로 공격 가능한 취약점을 더 정확하게 탐지할 수 있음을 보여준다.

다만 Recall 97.14%는 실험에서 구축한 35개 취약점 정답 집합에 대한 결과이며, 분석 대상 프로그램에 존재하는 모든 취약점에 대한 탐지율은 아니다.

#### Ablation Study

저자들은 각 구성 요소가 탐지 성능에 미치는 영향을 평가하였다.

| 실험 구성 | 탐지 취약점 |
|---|---:|
| 전체 AgentFuzz | 34개 |
| Seed Generation 제거 | 19개 |
| Seed Scheduling 제거 | 26개 |
| Semantic Score 제거 | 27개 |
| Seed Mutation 제거 | 25개 |

가장 큰 성능 감소는 Seed Generation을 제거했을 때 나타났다.

이는 LLM 에이전트에서 특정 기능을 실행할 수 있는 자연어 Seed를 생성하는 과정이 취약점 탐지에 중요한 역할을 한다는 점을 보여준다.

또한 Semantic Score를 제거했을 때 탐지 성능이 감소한 것은 코드상의 거리만으로는 Seed의 실제 유용성을 충분히 평가하기 어렵다는 점을 뒷받침한다.

### 5.5 AgentFuzz의 연구적 의의

AgentFuzz의 가장 중요한 기여는 기존 퍼징 기술을 단순히 LLM 환경에 적용한 것이 아니라, **LLM 에이전트의 동작 특성에 맞게 퍼징의 입력 생성, 피드백, 변형 과정을 재설계했다는 점**이다.

AFLGo에서 제안한 목표 지향적인 탐색 개념을 기반으로 하면서도 자연어 의미를 Seed Scheduling에 추가하였다.

또한 LLMSmith에서 제기된 위험한 실행 경로의 실제 공격 가능성 검증 문제를 자동화된 퍼징으로 해결하려고 하였다.

이를 통해 기존 정적 분석이 주로 잠재적인 위험 경로를 탐지했다면, AgentFuzz는 실제로 취약점이 발생하는 프롬프트를 생성하는 방향으로 발전하였다.

### 5.6 한계점 및 아쉬운 점

AgentFuzz에도 몇 가지 한계가 존재한다.

**첫째, 단일 프롬프트 기반 탐지에 집중한다.**

실제 에이전트에서는 여러 대화와 작업을 거치면서 상태가 변화하고 취약점이 발생할 수 있다.

그러나 AgentFuzz는 개별 프롬프트를 중심으로 취약점을 탐색하므로 복잡한 다단계 상호작용에서 발생하는 문제를 충분히 탐지하기 어렵다.

**둘째, 사전에 정의된 Sink에 의존한다.**

AgentFuzz는 코드 실행이나 SQL 실행과 같은 보안 민감 함수에 도달하는 취약점을 대상으로 한다.

따라서 자원 고갈이나 작업 수행 과정의 권한 남용처럼 특정 Sink 실행만으로 판단하기 어려운 보안 문제는 탐지 범위에 포함되지 않는다.

**셋째, 모델과 실행 환경에 대한 의존성이 존재한다.**

실험에서는 GPT-4o를 사용하였다.

그러나 LLM에 따라 자연어 해석과 도구 선택 결과가 달라질 수 있으므로 다른 모델에서도 동일한 탐지 성능이 나타나는지는 추가적인 검증이 필요하다.

**넷째, 높은 탐지 성능이 완전한 취약점 탐지를 의미하지 않는다.**

AgentFuzz의 높은 Precision은 탐지한 결과가 실제 취약점이었다는 의미이지, 존재하는 모든 취약점을 발견했다는 의미는 아니다.

따라서 미지의 취약점에 대한 탐지 성능과 다양한 실행 환경에서의 재현성을 추가로 평가할 필요가 있다.

## 6. 후속 연구 ①: AgentDoS (2026)

### 6.1 AgentFuzz 이후 새롭게 제기된 문제

AgentFuzz는 위험한 Sink에 도달하는 Taint-style Vulnerability를 효과적으로 탐지하였다.

그러나 에이전트에서는 특정 위험 함수에 도달하지 않더라도 보안 문제가 발생할 수 있다.

대표적인 사례가 자원 고갈로 인한 DoS 취약점이다.

예를 들어 에이전트가 사용자의 요청에 따라 대용량 파일을 반복적으로 다운로드하거나 대화 기록을 계속 저장한다면, 정상적인 기능을 수행하는 과정에서도 시스템의 메모리와 디스크가 고갈될 수 있다.

이러한 문제는 기존 AgentFuzz의 탐지 방식으로 해결하기 어렵다.

AgentFuzz에서 중요한 것은 특정 Sink에 도달하는 것이지만, DoS 취약점에서는 Sink에 도달한 이후 실제 자원이 얼마나 소비되는지까지 고려해야 하기 때문이다.

또한 DoS는 단일 요청에서 발생할 수도 있고 여러 요청에 걸쳐 누적될 수도 있다.

따라서 자원 사용량과 자원의 생명주기를 고려하는 새로운 퍼징 기법이 필요하다.

### 6.2 AgentDoS의 핵심 아이디어

AgentDoS는 2026년 USENIX Security에서 발표된 연구로, 자원 생명주기 분석과 Directed Greybox Fuzzing을 결합하였다.

AgentDoS의 가장 중요한 특징은 자원을 다음 세 가지 유형으로 구분한다는 것이다.

**① Short-lived Resource**

단일 요청 동안 사용되고 요청이 종료되면 해제되는 자원이다.

이 유형의 DoS를 발생시키려면 하나의 요청에서 충분한 자원을 소비하도록 해야 한다.

**② Long-lived Resource**

동일한 대화 세션에서 여러 요청에 걸쳐 유지되며 세션이 종료되면 해제되는 자원이다.

이 유형에서는 하나의 세션에서 여러 요청을 반복하여 자원 소비를 누적시킬 수 있다.

**③ Full-lifecycle Resource**

세션이 종료된 이후에도 유지되는 자원이다.

이 유형에서는 여러 세션을 거치면서 자원 사용량이 누적될 수 있다.

AgentDoS는 이러한 분류를 기반으로 각 자원의 특성에 맞는 퍼징 전략을 적용한다.

또한 Seed Scheduling 과정에서 Functionality Score뿐 아니라 Resource Consumed Score를 사용한다.

따라서 목표 기능을 실행하는 프롬프트 중에서도 실제 자원 소비량이 높은 입력을 우선적으로 탐색할 수 있다.

### 6.3 실험 결과

AgentDoS는 20개의 오픈소스 LLM 에이전트를 분석하여 총 36개의 새로운 DoS 취약점을 발견하였다.

이 취약점들은 16개의 에이전트에서 발견되었으며, 논문 발표 당시 15개의 CVE가 부여되었다.

저자들은 AgentFuzz를 DoS 탐지에 맞게 조정한 비교 실험도 수행하였다.

| 평가 항목 | AgentFuzz | AgentDoS |
|---|---:|---:|
| 탐지 취약점 | 3개 | 36개 |
| Precision | 100% | 100% |
| Recall | 7.9% | 94.7% |

이 비교는 38개의 DoS 취약점으로 구성된 평가 집합을 대상으로 수행되었다.

따라서 AgentDoS가 모든 보안 취약점에서 더 뛰어나다는 의미는 아니다. DoS의 특성에 맞게 자원 사용량과 생명주기를 고려한 설계가 해당 취약점 탐지에 효과적이었다는 의미이다.

### 6.4 AgentFuzz에서 어떻게 확장되었는가?

AgentDoS는 AgentFuzz의 Directed Greybox Fuzzing 접근을 유지하면서 퍼징의 목표를 확장하였다.

AgentFuzz에서는 특정 코드 위치까지의 거리와 자연어 의미가 중요한 피드백이었다.

반면 AgentDoS에서는 목표 기능 실행 여부뿐 아니라 메모리와 디스크 사용량이 중요한 피드백이 된다.

또한 퍼징의 단위가 단일 프롬프트에서 여러 프롬프트가 누적되는 세션으로 확장되었다.

즉, 연구의 관심이 **위험한 코드가 실행되는가?**에서 **정상적인 기능이 어떤 조건에서 시스템 전체의 가용성을 침해하는가?**로 확장되었다고 볼 수 있다.

다만 AgentDoS 역시 메모리와 디스크 자원 고갈에 집중하므로 CPU, 네트워크, API 호출 비용이나 복잡한 에이전트 상태 변화에 따른 가용성 문제를 모두 다루지는 못한다.

## 7. 확장 연구 ②: SkillScope (2026)

### 7.1 취약점 탐지 이후의 새로운 문제

AgentFuzz와 AgentDoS는 입력을 생성하고 변형하여 실제 취약점을 발견하는 데 집중하였다.

그러나 LLM 에이전트의 보안 문제는 취약점이 있는 코드를 실행할 때만 발생하는 것은 아니다.

에이전트가 정상적인 기능을 사용하더라도 사용자 요청에 필요하지 않은 행동을 수행한다면 보안 문제가 발생할 수 있다.

예를 들어 사용자가 GitHub 저장소의 코드를 분석해 달라고 요청했는데, 에이전트가 작업과 관련 없는 환경 설정 파일을 읽거나 외부 서버로 데이터를 전송하는 경우를 생각할 수 있다.

이러한 행동은 반드시 코드 실행 취약점이나 SQL Injection을 통해 발생하는 것은 아니다.

오히려 에이전트가 정상적으로 사용할 수 있는 도구를 과도하게 사용하면서 발생할 수 있다.

따라서 기존 취약점 탐지와 별개로 에이전트가 실제로 수행하는 행동의 필요성과 권한을 검증해야 한다.

### 7.2 SkillScope의 핵심 아이디어

SkillScope는 2026년 ACM CCS 연구로, Agent Skill이 사용자 요청 범위를 벗어나는 행동을 수행하는지 탐지하고 제한하는 프레임워크이다.

SkillScope의 핵심 아이디어는 특정 행동이 위험한지 여부뿐 아니라 **해당 행동이 현재 사용자 요청에 허가되어 있고 필요한 행동인지** 판단한다는 것이다.

이를 위해 두 가지 기준을 사용한다.

**Authorization**

해당 행동이 사용자 요청에 의해 허가되었는지 판단한다.

**Necessity**

해당 행동을 수행하지 않아도 사용자가 요청한 작업을 정상적으로 완료할 수 있는지 판단한다.

SkillScope는 이 두 기준을 사용하여 과도한 권한 사용을 판정한다.

### 7.3 방법론

SkillScope는 세 단계로 구성된다.

**① Unified Execution Graph Construction**

Skill의 자연어 지침과 실행 코드를 하나의 실행 그래프로 표현한다.

이를 통해 자연어 지침에서 실행되는 행동과 실제 코드에서 수행되는 연산을 함께 분석한다.

**② Action Over-Privilege Validation**

특정 행동이 실제 작업에 필요한지 검증한다.

이 과정에서 원래 Skill을 실행한 결과와 의심스러운 행동을 제거한 상태에서 다시 실행한 결과를 비교한다.

해당 행동을 제거하더라도 사용자가 요청한 작업이 정상적으로 완료된다면 불필요한 행동일 가능성이 높다.

또한 현재 사용자 요청에서 해당 행동이 허가되었는지도 함께 확인한다.

**③ Control-flow Privilege Constraining**

과도한 권한 사용으로 판단된 행동을 제한한다.

이때 기능을 무조건 삭제하지 않고 현재 사용자 요청에 필요한 경우에만 실행되도록 조건을 추가한다.

이를 통해 정상적인 기능을 유지하면서 불필요한 행동을 줄이도록 설계하였다.

### 7.4 실험 결과

SkillScope는 200개의 Skill로 구성된 평가 집합에서 94.53%의 F1 Score를 기록하였다.

또한 실제 Skill 생태계에서 수집한 68,312개의 유효한 Skill을 분석한 결과, 6,590개에서 과도한 권한 사용 행동을 검증하였다.

권한 제어를 적용한 평가에서는 과도한 Action-in-Task 실행 사례를 88.56% 감소시켰다.

이는 단순히 위험한 행동을 발견하는 것에서 나아가 실제 실행 과정에서 이를 제한할 수 있음을 보여준다.

### 7.5 AgentFuzz와의 관계

SkillScope는 AgentFuzz의 퍼징 알고리즘을 직접 확장한 연구는 아니다.

그러나 두 연구 모두 LLM의 자연어 처리 결과가 실제 시스템 행동으로 연결되는 과정에서 발생하는 보안 문제를 다룬다는 공통점이 있다.

AgentFuzz가 사용자 입력이 위험한 함수에 도달하는지를 확인한다면, SkillScope는 실제 실행된 행동이 사용자 요청에 필요한 행동인지를 확인한다.

따라서 두 연구는 서로 다른 보안 문제를 다루지만 상호 보완적이라고 볼 수 있다.

AgentFuzz가 기술적인 취약점을 탐지하는 역할이라면, SkillScope는 정상 기능이라도 권한 범위를 벗어나면 제한해야 한다는 새로운 검증 기준을 제시한다.

이는 에이전트 보안 연구가 **취약점의 존재 여부를 확인하는 단계에서 실행 행동의 정당성을 검증하는 단계로 확장되고 있음**을 보여주는 사례라고 생각한다.

다만 SkillScope 역시 LLM의 비결정적인 동작과 사용자 요청 해석의 모호성에 영향을 받는다. 또한 자연어 지침에 제어 조건을 추가하는 것만으로 운영체제 수준의 접근 제어를 완전히 보장할 수는 없다.

따라서 실제 운영 환경에서는 강제적인 권한 분리 및 실행 환경 격리와 결합할 필요가 있다.

## 8. 다섯 편의 논문으로 살펴본 연구 흐름

### 8.1 전체 연구 흐름

다섯 논문의 관계는 다음과 같이 정리할 수 있다.

**1단계: 목표 지향적인 취약점 탐색**

- AFLGo (2017)
- 특정 코드 지점에 효율적으로 도달하기 위한 Directed Greybox Fuzzing 제안

**2단계: LLM 애플리케이션의 보안 위협 분석**

- LLMSmith (2024)
- LLM 출력이 실제 코드 실행으로 연결되는 과정에서 발생하는 취약점 분석

**3단계: LLM 에이전트 취약점 탐지 자동화**

- AgentFuzz (2025)
- 자연어 의미와 프로그램 실행 피드백을 결합한 자동 퍼징

**4단계: 새로운 취약점 유형과 실행 상태로 확장**

- AgentDoS (2026)
- 자원 사용량과 생명주기를 고려한 DoS 취약점 탐지

**5단계: 실행 행동의 정당성과 권한 검증으로 확장**

- SkillScope (2026)
- 사용자 요청에 대한 행동의 필요성 및 권한 검증

여기서 AFLGo와 LLMSmith는 서로 다른 선행 연구 축이며, AgentDoS와 SkillScope도 각각 다른 방향으로 발전한 연구라는 점이 중요하다.

따라서 다섯 논문을 하나의 직선적인 발전 과정으로 보기보다는, **퍼징과 LLM 애플리케이션 보안 연구가 AgentFuzz에서 만나고, 이후 취약점 탐지 범위 확대와 실행 행동 제어라는 두 방향으로 발전했다**고 해석하는 것이 적절하다.

### 8.2 연구별 비교

| 논문 | 핵심 문제 | 접근 방식 | 연구적 발전 |
|---|---|---|---|
| AFLGo | 목표 코드에 효율적으로 도달하기 어려움 | 거리 기반 Directed Fuzzing | 목표 지향적 탐색 |
| LLMSmith | LLM 애플리케이션의 RCE 위험 분석 부족 | 정적 분석 및 실제 공격 검증 | LLM 애플리케이션의 실행 취약점 분석 |
| AgentFuzz | 자연어 입력으로 실제 취약점 자동 탐지 어려움 | 의미 기반 Seed 생성과 Directed Fuzzing | 취약점 재현 자동화 |
| AgentDoS | 자원 고갈 DoS를 기존 퍼징으로 탐지하기 어려움 | 자원 생명주기 및 사용량 기반 퍼징 | 취약점 유형과 실행 상태 확장 |
| SkillScope | 정상 도구를 이용한 과도 권한 사용 | 행동 그래프와 실행 재검증 | 행동 수준의 최소 권한 제어 |

## 9. LLM 에이전트 보안 연구의 주요 트렌드

다섯 논문을 분석하면서 발견한 연구 트렌드는 크게 네 가지이다.

### 9.1 정적 분석에서 실제 실행 기반 검증으로 발전

첫 번째 트렌드는 정적 분석으로 발견한 잠재적 취약점을 실제 실행을 통해 검증하는 방향으로 발전하고 있다는 것이다.

LLMSmith는 정적 분석으로 Source에서 Sink까지의 호출 경로를 식별하였다.

그러나 호출 경로가 존재한다는 사실만으로 취약점이 실제 발생한다고 판단하기 어렵다는 한계가 있었다.

AgentFuzz는 이러한 한계를 해결하기 위해 입력을 자동으로 생성하고 실제 에이전트를 실행하면서 취약점 발생 여부를 확인하였다.

이후 AgentDoS도 실제 자원 사용량과 서비스 상태를 관찰하여 DoS를 검증하였다.

SkillScope에서는 원래 Skill과 특정 행동을 제거한 Skill을 각각 실행한 후 결과를 비교하여 행동의 필요성을 검증한다.

이러한 흐름을 통해 **코드상으로 발생 가능해 보이는 문제를 찾는 것에서 실제 실행 결과로 문제를 입증하는 방향으로 연구가 발전하고 있다**고 볼 수 있다.

### 9.2 코드 중심 분석에서 자연어 의미와 시스템 상태를 함께 고려하는 분석으로 발전

두 번째 트렌드는 분석에 사용하는 정보가 다양해지고 있다는 것이다.

AFLGo는 프로그램의 CFG와 Call Graph를 통해 목표 코드까지의 거리를 계산하였다.

AgentFuzz는 여기에 자연어의 의미를 추가하였다.

즉, 코드상으로 가까운 입력인지뿐 아니라 목표 기능을 실행할 가능성이 높은 프롬프트인지를 함께 평가하였다.

AgentDoS는 여기서 한 단계 더 나아가 실제 시스템의 메모리와 디스크 사용량, 자원이 유지되는 기간을 분석에 포함하였다.

SkillScope는 사용자 요청과 실행 행동의 관계를 분석 기준으로 활용한다.

이러한 변화는 LLM 에이전트 보안에서 단순히 코드만 분석하는 것으로는 충분하지 않다는 점을 보여준다.

**앞으로의 보안 분석은 자연어 의미, 코드 실행 경로, 시스템 상태, 사용자 권한을 종합적으로 고려하는 방향으로 발전할 가능성이 높다고 생각한다.**

### 9.3 취약점 탐지 범위의 확대

세 번째 트렌드는 연구 대상이 특정 취약점에서 다양한 보안 속성으로 확장되고 있다는 것이다.

LLMSmith는 주로 RCE 취약점을 분석하였다.

AgentFuzz는 코드 인젝션, SQL Injection, SSTI 등 다양한 Taint-style Vulnerability를 탐지하였다.

AgentDoS는 기존의 Sink 기반 탐지로는 충분히 다루기 어려웠던 자원 고갈 DoS를 대상으로 하였다.

SkillScope는 취약점이 존재하지 않더라도 에이전트가 과도한 권한을 사용하는 상황을 보안 문제로 정의하였다.

이는 보안 연구에서 중요하게 생각하는 대상이 기밀성이나 무결성을 침해하는 취약점뿐 아니라 가용성, 권한 통제, 사용자 의도와의 일치성까지 확대되고 있음을 보여준다.

### 9.4 취약점 탐지에서 예방과 제어로 확장

네 번째 트렌드는 보안 문제를 발견하는 것에서 실제로 제한하는 방향으로 연구가 확장되고 있다는 것이다.

AFLGo, LLMSmith, AgentFuzz, AgentDoS는 주로 버그 또는 취약점의 발견과 재현에 집중하였다.

반면 SkillScope는 과도한 권한 사용을 발견한 이후 해당 행동을 조건부로 실행하도록 수정한다.

즉, 보안 문제가 발생할 수 있다는 사실을 알려주는 것뿐 아니라 정상적인 기능을 유지하면서 문제 발생을 줄이려는 시도이다.

이러한 접근은 실제 에이전트 서비스를 안전하게 운영하기 위해 중요하다고 생각한다.

다만 탐지 연구와 제어 연구는 서로 다른 목적을 가지므로 어느 한쪽이 다른 쪽을 대체한다고 보기는 어렵다.

오히려 취약점 탐지 결과를 바탕으로 실행 권한을 제한하고, 제한 이후에도 보안 조건이 유지되는지를 다시 검증하는 방식으로 결합될 수 있을 것이다.

## 10. 기존 연구들의 공통적인 한계

다섯 편의 논문은 각각 다른 문제를 해결했지만 공통적으로 남아 있는 한계도 존재한다.

### 10.1 복잡한 다단계 상호작용에 대한 검증 부족

LLM 에이전트는 실제 환경에서 하나의 요청만 처리하지 않는다.

여러 요청에 걸쳐 정보를 저장하고 다른 도구를 호출하며, 이전 작업 결과를 바탕으로 다음 행동을 결정한다.

AgentDoS는 자원 생명주기를 고려하여 일부 다단계 문제를 다루었지만, 일반적인 작업 상태 변화와 복잡한 실행 순서를 모두 검증하는 것은 아니다.

따라서 앞으로는 개별 프롬프트뿐 아니라 전체 작업 시퀀스를 분석 대상으로 삼을 필요가 있다.

### 10.2 탐지 범위와 평가 기준의 차이

각 논문은 서로 다른 취약점과 평가 데이터셋을 사용한다.

AgentFuzz의 Recall 97.14%와 AgentDoS의 Recall 94.7%는 각각 다른 취약점 정답 집합에서 계산된 결과이다.

또한 SkillScope의 F1 Score 94.53%는 최소 권한 위반 탐지를 평가한 수치이다.

따라서 이러한 수치를 직접 비교하여 어떤 연구가 더 우수하다고 판단하는 것은 적절하지 않다.

특히 미지의 취약점이 존재하는 상황에서는 완전한 정답 집합을 구축하기 어렵기 때문에 실제 전체 취약점에 대한 Recall을 정확하게 계산하기 어렵다.

앞으로는 공통된 평가 환경과 재현 가능한 벤치마크를 구축하는 것이 중요하다고 생각한다.

### 10.3 LLM의 비결정성과 재현성

LLM 에이전트는 동일한 프롬프트를 전달하더라도 모델이나 실행 환경에 따라 서로 다른 결과를 생성할 수 있다.

따라서 특정 프롬프트로 한 번 취약점을 유발했다고 해서 항상 동일한 결과가 발생한다고 보장할 수는 없다.

또한 LLM 모델의 업데이트나 도구 사용 방식의 변화가 취약점 탐지 성능에 영향을 줄 수 있다.

이러한 특성을 고려하면 취약점 탐지 여부뿐 아니라 반복 실행 성공률과 모델 간 성능 차이도 평가할 필요가 있다.

### 10.4 탐지 자동화의 비용

LLM을 활용한 퍼징은 자연어 의미를 고려할 수 있다는 장점이 있지만, 반복적인 모델 호출과 실제 에이전트 실행에 비용이 발생한다.

또한 복잡한 시스템에서는 여러 프롬프트를 실행하고 자원 사용량을 측정해야 하므로 실험 시간이 길어질 수 있다.

따라서 향후 연구에서는 탐지 정확도뿐 아니라 실행 시간, 토큰 사용량, API 호출 비용 등도 함께 최적화하는 것이 중요할 것이다.

## 11. 앞으로의 연구 방향에 대한 생각

다섯 편의 논문을 분석한 결과, 앞으로 LLM 에이전트 보안 연구는 **실행 상태를 고려하는 자동 검증과 최소 권한 제어를 결합하는 방향**으로 발전할 가능성이 있다고 생각한다.

특히 다음 세 가지 방향이 중요하다고 판단하였다.

### 11.1 Stateful Agent Fuzzing

첫 번째는 여러 단계의 작업과 상태 변화를 고려하는 Stateful Agent Fuzzing이다.

기존 AgentFuzz는 개별 프롬프트가 특정 Sink에 도달하는지를 중심으로 탐색한다.

그러나 실제 에이전트에서는 이전 작업에서 저장한 정보나 도구 실행 결과가 이후 작업의 행동에 영향을 줄 수 있다.

예를 들어 첫 번째 요청으로 파일을 저장하고, 두 번째 요청으로 저장한 내용을 분석하며, 세 번째 요청으로 외부 서비스를 호출할 수 있다.

이 과정에서 개별 요청만 분석하면 발견하기 어려운 취약점이 발생할 수 있다.

따라서 향후 연구에서는 단일 프롬프트 대신 여러 프롬프트로 구성된 실행 시퀀스를 Seed로 활용할 수 있을 것이다.

또한 도구 실행 결과와 에이전트의 상태 변화를 관찰하여 새로운 상태에 도달하거나 보안 조건을 위반할 가능성이 높은 시퀀스를 우선적으로 탐색할 수 있다.

### 11.2 보안 불변조건 기반 검증

두 번째는 특정 Sink에 도달하는 것을 넘어 시스템이 반드시 유지해야 하는 보안 속성을 기준으로 검증하는 것이다.

예를 들어 다음과 같은 보안 불변조건을 정의할 수 있다.

- 사용자에게 허가되지 않은 파일에 접근해서는 안 된다.
- 작업 완료 후 임시 자원은 정상적으로 반환되어야 한다.
- 사용자의 명시적인 허가 없이 외부로 민감한 데이터를 전송해서는 안 된다.
- 한 사용자의 요청이 다른 사용자의 작업을 지속적으로 방해해서는 안 된다.

이러한 조건을 정의한 뒤 에이전트의 입력과 작업 시퀀스를 변형하며 조건 위반 여부를 탐색할 수 있다.

이 방식은 AgentFuzz의 자동 입력 생성과 AgentDoS의 상태 및 자원 분석, SkillScope의 행동 검증 개념을 연결하는 연구 방향이 될 수 있다고 생각한다.

다만 서로 다른 연구의 기술을 단순히 결합하는 것만으로는 충분하지 않다.

각 보안 속성에 대해 무엇을 관찰하고 어떤 조건을 위반으로 판단할 것인지 명확한 검증 기준을 설계해야 한다.

### 11.3 취약점 탐지와 실시간 권한 제어의 결합

세 번째는 탐지 결과를 실제 에이전트의 실행 제어로 연결하는 것이다.

AgentFuzz와 AgentDoS는 위험한 입력을 자동으로 탐색하는 데 강점이 있다.

반면 SkillScope는 행동이 현재 작업에 필요한지 평가하고 불필요한 실행을 제한한다.

이러한 접근을 결합하면 에이전트가 실제로 도구를 호출하기 전에 작업의 필요성과 권한을 검증하고, 위험한 행동이 발견되면 실행을 제한할 수 있을 것이다.

예를 들어 에이전트가 파일 읽기 도구를 호출하려는 상황에서 해당 파일 접근이 현재 사용자 요청에 필요한지 확인하는 것이다.

이와 함께 권한을 제한한 이후에도 정상적인 사용자 작업이 완료되는지 검증할 필요가 있다.

보안성이 높아지더라도 정상적인 기능이 지나치게 제한된다면 실질적으로 사용하기 어려운 시스템이 될 수 있기 때문이다.

따라서 향후 연구에서는 탐지율뿐 아니라 정상 작업 완료율, 불필요한 차단 비율, 실행 지연 등을 함께 평가해야 한다고 생각한다.

## 12. 결론 및 느낀 점

이번 논문 트렌드 분석을 통해 LLM 에이전트 보안 연구가 단순히 새로운 AI 공격을 찾아내는 데 그치지 않고, 기존 소프트웨어 보안 기술을 에이전트의 특성에 맞게 확장하는 방향으로 발전하고 있다는 점을 확인할 수 있었다.

가장 먼저 Directed Greybox Fuzzing은 특정 목표 코드에 효율적으로 도달하는 방법을 제안하였다. 기존 퍼징처럼 프로그램 전체를 탐색하는 대신 목표 지점까지의 거리를 활용하여 입력을 선택한다는 점에서 중요한 기술적 기반을 제공하였다.

이후 LLMSmith는 LLM 기반 애플리케이션에서 자연어 요청이 실제 코드 실행 취약점으로 연결될 수 있음을 보여주었다. 특히 단순히 위험한 코드가 존재하는지를 분석하는 것뿐 아니라 실제 애플리케이션에서 공격 가능한지 검증했다는 점이 의미 있었다.

그러나 이 두 연구만으로는 LLM 에이전트에 존재하는 취약점을 자동으로 탐지하는 데 한계가 있었다.

AFLGo는 자연어 입력의 의미를 고려하지 못했고, LLMSmith는 위험한 호출 경로를 발견하더라도 실제 취약점을 유발하는 프롬프트를 자동으로 생성하는 데 한계가 있었다.

AgentFuzz는 이러한 문제를 해결하기 위해 Directed Greybox Fuzzing과 LLM 기반 자연어 입력 생성을 결합하였다.

특히 단순히 코드상 목표와의 거리만 고려하는 것이 아니라 프롬프트의 의미적 적합성을 함께 평가하고, 실제 실행 결과를 바탕으로 입력을 반복적으로 변형한다는 점이 인상적이었다.

또한 Functionality Mutator와 Argument Mutator를 구분하여 목표 기능 실행과 내부 제약조건 만족을 서로 다른 문제로 다루었다는 점도 흥미로웠다.

이후 연구들의 발전 방향을 비교하면서는 취약점 탐지의 목표가 계속 확장되고 있다는 점을 확인할 수 있었다.

AgentDoS는 기존 AgentFuzz의 접근을 자원 고갈 DoS 취약점으로 확장하였다. 특히 자원의 생명주기에 따라 서로 다른 퍼징 전략을 사용한다는 점에서 에이전트의 실행 상태를 고려하는 연구의 필요성을 알 수 있었다.

SkillScope는 또 다른 관점에서 보안 문제를 정의하였다. 특정 행동이 위험한 함수인지 여부뿐 아니라 사용자가 요청한 작업에 필요한 행동인지 검증한다는 점이 인상적이었다.

이를 통해 **에이전트의 보안은 단순히 취약한 코드를 실행하지 않도록 만드는 문제를 넘어, 사용자에게 허가된 범위 안에서 필요한 행동만 수행하도록 보장하는 문제**라는 점을 생각하게 되었다.

다섯 편의 논문에서 공통적으로 발견한 특징은 기존 보안 기술을 그대로 적용하는 데 그치지 않고 새로운 시스템의 동작 특성에 맞게 분석 대상과 검증 기준을 수정했다는 것이다.

AFLGo는 목표 코드까지의 거리를, AgentFuzz는 자연어 의미를, AgentDoS는 자원 사용량과 생명주기를, SkillScope는 사용자 요청에 대한 행동의 필요성을 주요 분석 기준으로 사용하였다.

이러한 흐름을 보면서 보안 연구에서 중요한 것은 단순히 새로운 도구를 개발하는 것이 아니라, 해결하려는 문제의 특성에 맞는 평가 기준을 정의하는 것이라고 생각하였다.

앞으로 LLM 에이전트가 더욱 다양한 시스템과 연결되고 여러 작업을 자율적으로 수행하게 된다면 보안 위협도 더욱 복잡해질 것이다.

따라서 향후에는 자연어 입력, 실제 코드 실행, 자원 상태, 사용자 권한을 함께 고려하는 통합적인 보안 검증 기술이 중요해질 것으로 예상한다.

특히 여러 단계의 작업에서 발생하는 상태 변화와 권한 경계를 자동으로 검증하는 연구가 의미 있을 것이라고 생각한다.

**결과적으로 이번 다섯 편의 논문을 통해 확인한 핵심 연구 흐름은 '목표 지향적 코드 탐색 → LLM 애플리케이션 취약점 분석 → 자연어 기반 자동 취약점 탐지 → 자원 및 상태 기반 취약점 탐지 확장 → 행동 단위의 최소 권한 검증과 제어'로 정리할 수 있다.**

다만 이는 모든 논문이 하나의 기술을 순차적으로 개선했다는 것이 아니라 LLM 에이전트의 보안을 바라보는 관점과 해결하려는 문제의 범위가 점차 확장되고 있다고 볼 수 있다.
