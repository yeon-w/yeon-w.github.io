LLM 에이전트는 답변을 생성하는 데서 그치지 않고 파일이나 외부 도구를 사용할 수 있다. 그렇다면 에이전트가 읽는 텍스트에 악의적인 지시가 섞였을 때, 원래 사용자의 작업이 어떻게 달라질까? 이 질문을 직접 살펴보기 위해 AI Agent Security Playground를 구성했다.


## 실험 환경

Ubuntu 가상머신에 OpenClaw를 설치하고 CLI/TUI, Gateway, 모델 제공자 설정을 마쳤다. 기본 에이전트를 실행하고 명령을 입력할 수 있는 상태까지 확인했다. 실험에는 실제 계정이나 개인정보 대신 더미 데이터를 사용했다.

공격 경로는 두 가지로 나눴다.

- 직접 프롬프트 인젝션: 에이전트에 입력하는 메시지에 기존 지시와 충돌하는 요청을 넣는 방식

- 간접 프롬프트 인젝션: 문서, 검색 결과, 도구 응답처럼 에이전트가 읽는 외부 데이터에 지시를 숨기는 방식

두 경우 모두 에이전트의 답변이 바뀌었는지와 실제 도구 사용까지 이어졌는지를 구분하는 것이 중요하다.

## 현재까지의 실험 결과

프로젝트 실험 로그에는 직접 프롬프트 인젝션 시나리오가 성공으로 기록돼 있다. 다만 사용 모델, 반복 횟수, 도구 호출·승인 여부, 공개 가능한 실행 로그는 아직 정리되지 않았다. 따라서 현재 기록만으로 특정 도구 실행을 유도했다거나 재현 가능한 성공률을 확인했다고 말하기는 어렵다.

간접 프롬프트 인젝션도 여러 방식으로 시도했지만, 안정적으로 성공하는 결과는 확인하지 못했다. 다음 실험에서는 에이전트가 공격 문구가 담긴 외부 데이터를 실제로 읽었는지부터 확인하고, 그 뒤의 응답과 도구 사용을 단계별로 기록할 계획이다.

## 방어 설계에서 살펴본 점

외부 데이터는 작업에 필요한 정보일 수 있지만, 새로운 명령으로 신뢰해서는 안 된다. 이를 바탕으로 도구 권한 최소화, 위험한 작업의 승인 절차, 플러그인의 프롬프트 변경 권한 제한 등을 검토하고 있다. 아직 방어 설정의 효과를 실험으로 측정한 단계는 아니다.

앞으로는 정상 작업의 성공 여부와 공격 목표의 성공 여부를 별도로 기록하고, 같은 조건에서 방어 적용 전후를 비교하려 한다. AgentDojo를 이용한 평가 환경도 준비 중이다.

이번 프로젝트를 통해 프롬프트 인젝션 실험에서는 “이상한 답변이 나왔다”는 관찰만으로 결론을 내리기 어렵다는 점을 배웠다. 입력이 어디에서 왔는지, 에이전트가 무엇을 읽었는지, 어떤 도구를 선택·실행했는지까지 남겨야 결과를 설명하고 다시 검증할 수 있다.
