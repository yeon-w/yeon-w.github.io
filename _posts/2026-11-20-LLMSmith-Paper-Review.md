## 1. 서론: 연구 배경과 문제의식

### 1.1 LLM 기반 애플리케이션의 등장

대규모 언어 모델(LLM)의 발전과 함께 자연어를 사용하여 다양한 작업을 수행하는 애플리케이션이 증가하고 있다.

특히 LangChain, LlamaIndex와 같은 프레임워크를 활용하면 개발자는 LLM을 외부 도구 및 서비스와 쉽게 연결할 수 있다.

예를 들어 사용자가 자연어로 데이터 분석을 요청하면 LLM이 해당 요청을 해석하고 Python 코드를 생성하여 실제 데이터를 분석하는 방식이다.

이처럼 LLM에 코드 실행 기능을 결합하면 사용자는 복잡한 프로그래밍 작업을 직접 수행하지 않고도 다양한 기능을 사용할 수 있다.

그러나 이러한 구조에는 중요한 보안 문제가 존재한다.

**LLM이 생성한 코드를 충분히 검증하지 않고 실행하면, 공격자가 자연어 프롬프트만으로 서버에서 임의의 코드를 실행하도록 유도할 수 있다는 것이다.**

### 1.2 Remote Code Execution이란?

Remote Code Execution(RCE)은 공격자가 원격 시스템에서 임의의 명령어나 코드를 실행할 수 있는 취약점을 의미한다.

기존 웹 애플리케이션에서는 사용자 입력이 충분한 검증 없이 명령어 실행 함수나 코드 실행 함수에 전달될 때 RCE 취약점이 발생할 수 있다.

예를 들어 사용자 입력이 `eval()` 또는 `exec()`와 같은 함수에 직접 전달된다면 악의적인 코드가 실행될 가능성이 있다.

LLM 기반 애플리케이션에서는 여기에 LLM이라는 새로운 단계가 추가된다.

**사용자 입력 → LLM → 코드 생성 → 코드 실행 API → 서버에서 코드 실행**

이 구조에서는 공격자가 직접 코드를 입력하지 않더라도 자연어 요청을 통해 LLM이 위험한 코드를 생성하도록 유도할 수 있다.

따라서 프롬프트 인젝션이 단순히 모델의 응답을 변경하는 문제를 넘어 실제 서버의 보안 문제로 이어질 수 있다.

### 1.3 기존 연구의 한계

기존 LLM 보안 연구는 주로 모델 자체의 안전성을 평가하는 데 집중하였다.

대표적으로 Jailbreak나 Prompt Injection 연구에서는 공격자가 모델의 안전 정책을 우회하거나 원하지 않는 응답을 생성하도록 유도할 수 있는지를 분석하였다.

그러나 이러한 연구만으로는 LLM과 외부 실행 도구가 결합된 애플리케이션의 보안 문제를 충분히 설명하기 어렵다.

LLM이 악의적인 응답을 생성하더라도 실제 시스템에서 위험한 함수가 실행되지 않는다면 서버 수준의 보안 사고로 이어지지 않을 수 있다.

반대로 LLM이 생성한 코드가 별도의 검증 없이 실행된다면 단순한 프롬프트 조작이 심각한 시스템 침해로 이어질 수 있다.

따라서 LLM의 응답뿐 아니라 **LLM의 출력이 애플리케이션 내부에서 어떤 함수로 전달되고 실제로 어떻게 실행되는지** 분석할 필요가 있다.

저자들은 이러한 문제를 해결하기 위해 LLMSmith를 제안하였다.

## 2. 문제 정의와 연구 목표

본 논문은 LLM 기반 프레임워크에서 발생할 수 있는 RCE 취약점을 자동으로 탐색하고, 해당 프레임워크를 사용하는 실제 애플리케이션에서 취약점이 악용 가능한지 검증하는 것을 목표로 한다.

이를 위해 세 가지 연구 문제를 제시하였다.

### 2.1 위험한 코드 실행 경로를 어떻게 탐지할 것인가?

LangChain과 같은 프레임워크에는 다양한 API와 클래스, 함수가 존재한다.

이러한 코드 전체를 분석하면서 사용자 입력이 코드 실행 함수에 도달하는 경로를 찾는 것은 복잡한 작업이다.

특히 Python은 동적인 함수 호출과 객체 지향적 구조를 지원하기 때문에 단순한 정적 분석만으로 호출 관계를 정확하게 추적하기 어렵다.

따라서 대규모 프레임워크에서도 효율적으로 위험한 API를 식별하는 분석 방법이 필요하다.

### 2.2 취약한 프레임워크를 사용하는 애플리케이션을 어떻게 찾을 것인가?

특정 프레임워크에 취약점이 존재하더라도 이를 사용하는 모든 애플리케이션이 실제로 공격 가능한 것은 아니다.

어떤 애플리케이션은 위험한 API를 사용하지 않을 수 있으며, 다른 애플리케이션은 별도의 보안 장치를 적용했을 수도 있다.

따라서 취약한 프레임워크를 기반으로 개발되었으며 실제로 테스트할 수 있는 애플리케이션을 찾아야 한다.

### 2.3 실제 공격 가능성을 어떻게 검증할 것인가?

LLM 기반 애플리케이션은 프롬프트에 따라 실행 결과가 달라질 수 있다.

또한 시스템 프롬프트, 모델의 안전 정책, 코드 실행 환경의 제한 등 다양한 요인이 공격 성공 여부에 영향을 준다.

따라서 단순히 위험한 함수 호출 경로가 존재한다는 사실만으로는 실제 취약점이 발생한다고 단정할 수 없다.

저자들은 이러한 문제를 해결하기 위해 정적 분석과 실제 프롬프트 기반 테스트를 결합하였다.

## 3. 핵심 아이디어: LLMSmith

LLMSmith는 LLM 기반 프레임워크에서 위험한 API를 식별하고, 실제 애플리케이션에서 해당 취약점의 악용 가능성을 검증하기 위한 분석 프레임워크이다.

전체 과정은 크게 세 단계로 구성된다.

**① Vulnerable Framework API Detection**

프레임워크의 소스코드를 분석하여 사용자 입력으로부터 위험한 코드 실행 함수까지 이어지는 호출 경로를 탐색한다.

**② Potentially Affected Apps Collection**

위험한 API를 사용하는 애플리케이션을 검색하고 분석 대상을 수집한다.

**③ Prompt-based Exploitation**

수집한 애플리케이션에 프롬프트를 전달하여 실제로 임의 코드 실행이 발생하는지 검증한다.

이러한 구조의 핵심은 프레임워크 수준의 잠재적 취약점과 실제 배포된 애플리케이션의 공격 가능성을 구분하여 분석한다는 점이다.

## 4. 방법론 및 시스템 구성

### 4.1 Vulnerable Framework API Detection

첫 번째 단계는 위험한 코드 실행 API를 탐지하는 것이다.

LLMSmith는 정적 분석을 활용하여 사용자 입력을 받는 API와 보안에 민감한 함수 사이의 호출 관계를 추출한다.

이때 중요한 개념은 다음과 같다.

- **Source:** 외부 입력이 전달되는 지점
- **Sink:** 보안에 민감한 동작을 수행하는 함수
- **Call Chain:** Source에서 Sink에 도달하기까지 이어지는 함수 호출 관계

예를 들어 다음과 같은 호출 관계를 생각할 수 있다.

`User Input → create_pandas_dataframe_agent → PythonAstREPLTool._run → exec()`

사용자 요청이 LLM을 거쳐 실행 가능한 Python 코드로 변환되고, 최종적으로 `exec()` 함수에 전달될 수 있다.

LLMSmith는 이러한 호출 경로를 찾아 잠재적으로 위험한 API를 식별한다.

#### Dynamic Call Chain Extraction

LLMSmith의 핵심 기술 중 하나는 Dynamic Call Chain Extraction이다.

이름에 Dynamic이라는 표현이 포함되어 있지만, 실제로 프로그램 실행을 추적하는 동적 분석이 아니라 **대규모 코드베이스에서 필요한 호출 관계를 선택적으로 추출하는 정적 분석 방식**이다.

일반적인 정적 분석은 프로그램의 전체 호출 그래프를 구축하려고 한다.

하지만 대규모 프레임워크에서는 이러한 분석에 상당한 시간과 메모리가 필요하다.

LLMSmith는 이를 해결하기 위해 위험한 Sink에서 분석을 시작한다.

먼저 `eval()`, `exec()` 등 코드 실행 함수를 찾고, 해당 함수를 호출하는 상위 함수를 역방향으로 추적한다.

이후 사용자 입력을 받는 API까지 호출 경로가 이어지는지 확인한다.

이러한 방식은 분석 범위를 위험한 함수와 관련된 코드로 제한할 수 있다는 장점이 있다.

또한 Python에서 발생하는 클래스 상속과 암묵적 함수 호출을 처리하기 위한 분석 규칙을 추가한다.

다만 LLMSmith는 상세한 데이터 흐름 분석을 자동으로 수행하지 않기 때문에 추출된 호출 경로의 도달 가능성을 확인하는 데 수동 검증이 사용된다.

### 4.2 Potentially Affected Apps Collection

두 번째 단계는 위험한 API를 사용하는 실제 애플리케이션을 수집하는 것이다.

저자들은 애플리케이션을 크게 두 가지로 구분하였다.

**① White-box Applications**

소스코드를 확인할 수 있는 애플리케이션이다.

LLMSmith는 GitHub 등 코드 저장소에서 위험한 API를 사용하는 프로젝트를 검색한다.

이후 프로젝트의 README 및 설명 파일을 분석하여 실제 배포된 애플리케이션의 URL을 추출한다.

**② Black-box Applications**

소스코드를 확인할 수 없는 애플리케이션이다.

이 경우 직접 코드의 사용 여부를 확인할 수 없으므로 애플리케이션의 설명이나 기능적 특징을 활용한다.

LLMSmith는 White-box 애플리케이션의 설명에서 추출한 키워드를 바탕으로 유사한 기능을 제공하는 애플리케이션을 검색한다.

이를 통해 소스코드가 공개되지 않은 서비스까지 분석 범위를 확장한다.

### 4.3 Prompt-based Exploitation

세 번째 단계는 실제 애플리케이션에서 취약점을 검증하는 것이다.

이 과정에서는 프롬프트를 전달하고 애플리케이션의 응답을 관찰하여 코드 실행 여부와 공격 가능성을 확인한다.

LLMSmith는 다음과 같은 단계로 테스트를 수행한다.

**① Basic Usage Test**

애플리케이션이 정상적으로 작동하며 사용자 입력을 처리할 수 있는지 확인한다.

정상적인 질문에 응답하지 못하는 애플리케이션은 이후 테스트에서 신뢰할 만한 결과를 얻기 어렵다.

**② Hallucination Test**

LLM이 실제로 코드를 실행한 것인지, 단순히 코드 실행 결과처럼 보이는 답변을 생성한 것인지 구분한다.

예를 들어 복잡한 해시 계산이나 인코딩 작업을 요청했을 때 정답을 생성했다는 사실만으로 코드 실행을 확정할 수는 없다.

따라서 LLMSmith는 여러 계산 문제를 활용하여 코드 실행 기능이 존재할 가능성을 예비적으로 평가한다.

이후 실제 명령 실행 테스트를 통해 결과를 추가로 확인한다.

**③ RCE Test**

애플리케이션에 테스트용 프롬프트를 전달하여 실제로 시스템 명령어를 실행할 수 있는지 확인한다.

이때 기대한 명령어 실행 결과가 나타나는지를 기준으로 판단한다.

**④ Escape Test**

일반적인 프롬프트가 실행되지 않는 경우, 모델의 출력 제한과 코드 실행 환경의 제약이 공격 성공 여부에 어떤 영향을 미치는지 확인한다.

논문에서는 이를 LLM Escape와 Code Escape로 구분하였다.

LLM Escape는 모델이 원하는 코드를 생성하지 않는 문제를 다루며, Code Escape는 생성된 코드가 실행 환경의 제한 때문에 실행되지 못하는 문제를 다룬다.

두 방식은 서로 다른 단계에서 발생하는 제약을 다룬다는 점에서 차이가 있다.

**⑤ Network Access Test 및 Backdoor Test**

코드 실행이 확인되면 외부 네트워크 접근이 가능한지 등 추가적인 실행 환경의 특성을 확인한다.

저자들은 이러한 테스트를 통해 단순한 코드 실행에서 서버 제어로 이어질 수 있는 위험성을 평가하였다.

이처럼 LLMSmith는 취약점 존재 여부뿐 아니라 실제로 발생할 수 있는 피해의 범위도 분석하였다.

## 5. 실험 및 평가

저자들은 LLMSmith를 검증하기 위해 11개의 LLM 기반 프레임워크와 실제 배포된 애플리케이션 51개를 분석하였다.

### 5.1 프레임워크 취약점 탐지

LLMSmith는 11개 프레임워크에서 다음과 같은 결과를 얻었다.

| 평가 항목 | 결과 |
|---|---:|
| 분석한 프레임워크 | 11개 |
| 추출한 Call Chain | 51개 |
| 식별한 User-level API | 18개 |
| 발견한 취약점 | 20개 |
| RCE 취약점 | 19개 |
| 임의 파일 읽기/쓰기 취약점 | 1개 |
| 부여된 CVE | 13개 |

발견한 취약점 중 17개는 프레임워크 개발자로부터 확인을 받았으며, 13개에는 CVE가 부여되었다.

또한 이 중 6개는 CVSS 9.8점을 기록하여 심각한 수준의 보안 위험을 보여주었다.

이러한 결과는 LLM 기반 프레임워크에서 코드 실행 기능이 실제 보안 취약점으로 연결될 수 있음을 확인한 것이다.

### 5.2 기존 정적 분석 도구와 비교

저자들은 기존 Python 정적 분석 도구인 PyCG와 LLMSmith를 비교하였다.

| 평가 항목 | PyCG | LLMSmith |
|---|---:|---:|
| 추출한 Call Chain | 13개 | 51개 |
| 대규모 프레임워크 분석 | 일부 시간 초과 | 분석 완료 |

PyCG는 LangChain과 LlamaIndex처럼 규모가 큰 프레임워크를 분석하는 과정에서 시간 제한을 초과하였다.

반면 LLMSmith는 위험한 함수에서 역방향으로 필요한 호출 경로만 탐색하여 분석 효율성을 높였다.

이는 프로그램 전체의 호출 그래프를 구성하는 것보다 분석 목적에 맞게 범위를 제한하는 것이 유용할 수 있음을 보여준다.

다만 추출된 호출 경로가 모두 실제 취약점으로 이어지는 것은 아니므로, 호출 경로의 정확성과 공격 가능성은 별도로 검증할 필요가 있다.

### 5.3 실제 애플리케이션 공격 검증

LLMSmith는 51개의 실제 LLM 기반 애플리케이션을 대상으로 취약점 검증을 수행하였다.

그 결과 17개 애플리케이션에서 공격에 성공하였다.

| 평가 항목 | 결과 |
|---|---:|
| 테스트한 애플리케이션 | 51개 |
| 공격 성공 애플리케이션 | 17개 |
| RCE 발생 | 16개 |
| SQL Injection 발생 | 1개 |
| Reverse Shell 실행 확인 | 14개 |
| Root 권한 획득 확인 | 4개 |

이는 프레임워크의 위험한 API가 실제 애플리케이션에서 사용될 때 심각한 보안 문제로 연결될 수 있다는 점을 보여준다.

특히 코드 실행 취약점이 발생한 일부 환경에서는 서버 제어 및 권한 상승까지 가능했다.

다만 이 결과는 취약한 프레임워크를 사용할 가능성이 있는 애플리케이션을 선별하여 테스트한 결과이므로, 전체 LLM 애플리케이션의 취약점 발생 비율로 일반화해서는 안 된다.

### 5.4 공격 실패 원인 분석

저자들은 공격이 성공하지 않은 34개 애플리케이션의 실패 원인도 분석하였다.

주요 원인은 다음과 같다.

- 애플리케이션 내부의 Runtime Exception
- 사용자 프롬프트 입력에 대한 제한
- 코드 실행 기능의 부재
- 코드 실행에 대한 보호 장치
- 기타 환경적 요인

이러한 분석은 위험한 API가 존재하더라도 실제 실행 환경에 따라 취약점 발생 여부가 달라질 수 있음을 보여준다.

특히 적절한 실행 환경 격리는 RCE의 피해 범위를 줄이는 데 중요한 역할을 할 수 있다.

## 6. 한계점 및 아쉬운 점

### 6.1 정적 분석으로 실제 실행 가능성을 완전히 판단하기 어려움

LLMSmith는 위험한 함수와 사용자 입력 사이의 Call Chain을 추출한다.

그러나 두 함수 사이에 호출 관계가 존재한다는 사실이 실제 악용 가능한 데이터 흐름의 존재를 보장하지는 않는다.

예를 들어 코드 실행 함수까지 호출 경로가 연결되어 있더라도 해당 함수의 인자가 사용자 입력으로 제어되지 않는다면 RCE가 발생하지 않을 수 있다.

또한 특정 조건문에 의해 위험한 함수가 실행되지 않을 수도 있다.

따라서 정적 분석으로 발견한 경로는 잠재적인 취약점 후보이며, 실제 취약점 여부를 확인하기 위해 추가적인 동적 검증이 필요하다.

### 6.2 완전한 자동화가 이루어지지 않음

LLMSmith는 호출 경로 추출과 애플리케이션 검색 과정의 상당 부분을 자동화하였다.

그러나 호출 경로의 도달 가능성을 검증하거나 실제 애플리케이션의 동작에 맞게 프롬프트를 수정하는 과정에는 사람의 개입이 필요할 수 있다.

또한 프롬프트 기반 공격 테스트에서도 사전에 정의된 프롬프트 템플릿을 활용한다.

따라서 새로운 형태의 취약점이나 예상하지 못한 실행 조건을 자동으로 탐색하는 데에는 한계가 있다.

이러한 점에서 LLMSmith는 완전히 자동화된 취약점 탐지 시스템이라기보다는 정적 분석과 체계적인 공격 검증을 결합한 연구 도구에 가깝다고 생각한다.

### 6.3 RCE 중심의 제한된 취약점 탐지 범위

LLMSmith는 코드 실행 함수에 초점을 맞춘다.

따라서 SQL Injection, 파일 접근 제어 문제, 도구 사용 권한 문제 등 다양한 보안 취약점을 포괄적으로 탐지하도록 설계된 것은 아니다.

물론 실제 애플리케이션 검증에서는 SQL Injection 사례도 발견되었지만, 핵심 분석 대상은 RCE를 유발할 수 있는 프레임워크 API이다.

따라서 보다 다양한 보안 민감 함수와 데이터 흐름을 고려하도록 확장할 필요가 있다.

### 6.4 애플리케이션과 실행 환경에 대한 의존성

실험 대상은 주로 Python 기반 LLM 프레임워크 및 웹 애플리케이션이다.

따라서 다른 프로그래밍 언어나 프레임워크에서도 동일한 탐지 성능을 보일지는 추가 검증이 필요하다.

또한 실제 서비스에서는 LLM 모델, 시스템 프롬프트, 실행 환경 격리, 네트워크 정책 등이 공격 성공 여부에 영향을 준다.

이러한 요소에 따라 동일한 프롬프트라도 다른 결과가 발생할 수 있으므로 탐지 결과의 재현성을 높이기 위한 연구도 필요하다고 생각한다.

## 7. 내가 생각하는 후속 연구 방향

### 7.1 Directed Fuzzing을 활용한 자동화

가장 먼저 확장해 보고 싶은 방향은 정적 분석으로 발견한 위험한 함수 경로를 Directed Fuzzing의 목표로 활용하는 것이다.

LLMSmith는 위험한 함수와 연결된 API를 식별할 수 있지만, 해당 경로를 실행하기 위한 프롬프트를 자동으로 최적화하는 기능은 제한적이다.

반면 Directed Greybox Fuzzing은 목표 코드까지의 거리를 활용하여 입력을 반복적으로 변형할 수 있다.

따라서 LLMSmith의 정적 분석 결과를 목표 지점으로 설정하고, 실제 실행 피드백을 활용하여 자연어 프롬프트를 자동으로 변형하는 방식을 고려할 수 있다.

이러한 방향은 AgentFuzz가 실제로 발전시킨 접근 방식과 연결된다.

### 7.2 LLM 기반 프롬프트 생성

또 다른 방향은 LLM을 활용하여 취약점 탐지에 적합한 프롬프트를 자동으로 생성하는 것이다.

LLMSmith에서는 사전에 정의된 공격 프롬프트를 활용하고, 필요에 따라 사람이 입력을 조정한다.

그러나 애플리케이션마다 제공하는 기능과 프롬프트 해석 방식이 다르기 때문에 고정된 프롬프트만으로는 다양한 실행 경로를 탐색하기 어렵다.

따라서 함수명, API 설명, 실행 결과 등을 LLM에 제공하고 목표 기능을 호출할 수 있는 프롬프트를 자동으로 생성하도록 개선할 수 있을 것이다.

이러한 접근을 통해 사람의 개입을 줄이고 분석 대상이 달라지더라도 적용할 수 있는 자동화 수준을 높일 수 있다.

### 7.3 다양한 Taint-style Vulnerability 탐지

마지막으로 RCE 외의 다양한 보안 취약점을 탐지하도록 확장하는 방향도 생각해 볼 수 있다.

예를 들어 사용자 입력이 데이터베이스 쿼리 실행 함수나 파일 접근 함수로 전달되는 경로를 분석할 수 있다.

이후 각 Sink에 적합한 입력 조건을 생성하고, 실제로 보안 문제가 발생하는지 검증하는 것이다.

이를 통해 특정 유형의 코드 실행 취약점뿐 아니라 LLM 에이전트의 여러 기능에서 발생할 수 있는 보안 문제를 종합적으로 탐색할 수 있을 것이다.

## 8. 결론 및 느낀 점

이 논문을 읽으며 가장 인상적이었던 점은 LLM의 보안 문제를 모델 자체가 아니라 모델과 연결된 애플리케이션의 실행 구조에서 분석했다는 것이다.

기존의 Prompt Injection이나 Jailbreak 연구를 접했을 때에는 공격자가 모델이 원하지 않는 답변을 생성하도록 만드는 과정에 주로 관심을 두었다.

그러나 LLMSmith는 프롬프트를 통해 생성된 코드가 실제 서버의 함수로 전달되고 실행되는 과정까지 분석하였다.

이를 통해 LLM 보안에서 중요한 것은 단순히 모델이 악의적인 요청에 응답하는지 여부가 아니라, **모델의 출력이 실제 시스템에서 어떤 권한으로 실행되는지**라는 점을 알게 되었다.

또한 정적 분석과 실제 공격 검증을 결합한 방식도 흥미로웠다.

정적 분석을 통해 위험한 함수의 호출 경로를 빠르게 탐색하고, 실제 애플리케이션에 프롬프트를 전달하여 공격 가능성을 확인했다는 점에서 단순한 취약점 후보 탐지보다 실질적인 결과를 제공하였다.

하지만 정적 분석으로 위험한 경로를 발견하더라도 실제로 해당 경로를 실행하는 프롬프트를 생성하는 과정은 여전히 복잡하다. 특히 LLM의 비결정적인 동작과 애플리케이션마다 다른 실행 조건 때문에 완전한 자동화에 어려움이 존재한다.

이러한 관점에서 AgentFuzz의 필요성을 이해할 수 있었다.

AgentFuzz는 LLMSmith와 달리 실제 실행 피드백을 활용하여 Seed를 반복적으로 선택하고 변형한다. 또한 자연어 입력의 의미를 고려하여 목표 함수 실행 가능성을 높인다.

결과적으로 LLMSmith는 **LLM 기반 애플리케이션에 존재하는 RCE 취약점을 체계적으로 분석하고, 실제 서비스에서 공격 가능한지를 검증한 연구**라고 정리할 수 있다.

이번 논문을 통해 LLM 보안 연구에서도 전통적인 소프트웨어 보안 분석 기법인 정적 분석과 데이터 흐름 분석이 중요한 역할을 한다는 점을 배울 수 있었다.

또한 취약점이 존재할 가능성이 있는 코드를 찾아내는 것과 그 취약점을 실제로 재현하는 것은 서로 다른 문제이며, 두 과정을 연결하는 자동화 기술이 중요하다는 점을 확인할 수 있었다.
