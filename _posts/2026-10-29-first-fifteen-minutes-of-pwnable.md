CTF 포너블 문제를 처음 열면 곧바로 페이로드부터 떠올리기 쉽다. 하지만 **실행 환경을 먼저 기록**하면 이후의 관찰이 훨씬 정확해진다. 이 글은 특정 문제의 풀이 또는 획득한 플래그가 아니라, 허가된 연습 환경에서 쓸 분석 순서다.

## 1. 파일과 실행 조건

```bash
file ./chall
readelf -h ./chall
readelf -l ./chall
```

아키텍처(예: x86-64), 동적 링크 여부, 인터프리터 경로를 적는다. 제공된 `libc`나 로더가 있다면 그 파일명도 함께 기록한다. 로컬 실행 결과와 원격 결과가 다르면 먼저 이 차이를 의심한다.

## 2. 보호 기법은 이름보다 의미를 이해하기

환경에 `checksec`이 설치되어 있다면 `checksec --file=./chall`로 요약을 볼 수 있다. 출력은 아래 질문으로 다시 풀어 적는다.

| 항목 | 확인할 질문 |
| --- | --- |
| NX | 스택 같은 데이터 영역에서 코드를 실행할 수 있는가? |
| PIE | 실행할 때 프로그램의 기준 주소가 바뀌는가? |
| Canary | 함수 복귀 전에 스택 손상 검사가 있는가? |
| RELRO | 재배치 후 특정 영역의 쓰기 권한이 제한되는가? |

이 표만으로 취약점이 존재한다고 결론 내릴 수는 없다. 보호 기법은 **가능한 공격 경로의 제약**을 알려 줄 뿐이다.

## 3. 정상 입력과 경계 입력

프로그램을 허가된 로컬 환경에서 실행하고, 메뉴와 입력 길이 제한, 종료 조건을 기록한다. 같은 입력을 여러 번 보내 출력이 안정적인지 살핀다. 충돌이 나면 입력과 관찰된 현상부터 보존하고, 원인을 확정하기 전에는 "버퍼 오버플로"처럼 이름을 붙이지 않는다.

기록 형식은 간단하면 충분하다.

```text
환경: 운영체제 / 아키텍처 / 제공된 라이브러리
입력: 재현에 필요한 최소 입력
관찰: 출력, 종료 상태, 충돌 위치
가설: 관찰을 설명할 수 있는 원인
다음 실험: 가설을 구분할 입력 하나
```

## 4. 풀이를 쓸 때

나중에 실제 문제를 풀었다면 문제명과 공개 허용 여부를 확인한다. 글에는 사용한 바이너리의 해시, 도구 버전, 보호 기법, 핵심 관찰과 수정한 가설을 남기면 풀이의 재현성이 높아진다. 비공개 대회 중에는 문제 파일이나 플래그를 게시하지 않는다.
