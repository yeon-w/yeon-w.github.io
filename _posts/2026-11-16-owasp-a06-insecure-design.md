# [OWASP Top 10:2025] A06. Insecure Design - 코드는 정상인데 왜 취약점이 발생할까?

## 1. intro

웹 보안 취약점이라고 하면 보통 SQL Injection, XSS, 인증 우회처럼 공격자가 악의적인 입력을 전달하거나 개발자가 작성한 코드의 오류를 악용하는 상황이 먼저 떠오른다.

그런데 코드를 아무리 정확하게 작성해도 보안 취약점이 발생할 수 있다.

개발자가 의도한 대로 프로그램이 동작하고, 모든 기능이 정상적으로 실행되는데도 공격자가 시스템을 악용할 수 있는 경우가 있다. 이는 프로그램을 구현하는 과정이 아니라, 프로그램이 어떤 방식으로 동작해야 하는지 결정하는 설계 과정에서 문제가 발생했기 때문이다.

이번 글에서는 OWASP Top 10:2025의 A06에 해당하는 Insecure Design에 대해 공부하고, 안전하지 않은 설계가 실제로 어떤 보안 문제를 발생시키는지 정리해 보고자 한다.

---

## 2. OWASP Top 10이란?

OWASP(Open Worldwide Application Security Project)는 소프트웨어 보안 향상을 목적으로 활동하는 비영리 재단이자 오픈 커뮤니티이다. 개발자와 보안 전문가들이 안전한 소프트웨어를 개발할 수 있도록 다양한 보안 가이드라인, 교육 자료, 보안 도구 등을 제공한다.

OWASP에서 발표하는 대표적인 자료 중 하나가 OWASP Top 10이다.

OWASP Top 10은 웹 애플리케이션에서 주의해야 할 주요 보안 위험을 10가지 범주로 정리한 문서이다. 단순히 개별 취약점을 나열하는 것이 아니라, 개발자와 보안 전문가가 어떤 보안 위험에 집중해야 하는지 방향을 제시한다.

OWASP Top 10:2025에서는 다음과 같은 보안 위험을 다루고 있다.

| 순위 | 보안 위험 |
|---|---|
| A01 | Broken Access Control |
| A02 | Security Misconfiguration |
| A03 | Software Supply Chain Failures |
| A04 | Cryptographic Failures |
| A05 | Injection |
| A06 | Insecure Design |
| A07 | Authentication Failures |
| A08 | Software or Data Integrity Failures |
| A09 | Security Logging & Alerting Failures |
| A10 | Mishandling of Exceptional Conditions |

이번에 선택한 주제는 A06에 해당하는 Insecure Design이다.

Insecure Design은 2021년 OWASP Top 10에 처음 등장했으며, 당시에는 A04로 분류되었다. 2025년에는 A06으로 순위가 변경되었지만, 여전히 웹 애플리케이션의 중요한 보안 위험 중 하나이다.

## 3. Insecure Design이란?

### 3.1. 안전하지 않은 설계

Insecure Design은 직역하면 '안전하지 않은 설계'라는 의미이다.

시스템의 요구사항이나 구조, 기능의 동작 방식 등을 설계하는 과정에서 보안 위협을 충분히 고려하지 않아 발생하는 보안 위험을 의미한다.

쉽게 설명하면, 프로그램을 만들기 전에 정해 놓은 규칙 자체에 문제가 있는 것이다.

예를 들어 영화관 예약 시스템을 생각해 보자.

영화관은 사용자가 좌석을 선택하고 결제하면 예약이 완료되는 시스템을 만들었다. 그런데 설계 과정에서 다음과 같은 상황을 고려하지 않았다고 가정해 보자.

- 사용자가 좌석을 예약한 후 결제하지 않는다면 어떻게 해야 할까?
- 한 사람이 수백 개의 좌석을 동시에 예약한다면 어떻게 될까?
- 여러 사용자가 같은 좌석을 동시에 예약한다면 어떻게 처리해야 할까?

이러한 상황을 고려하지 않고 시스템을 개발하면, 코드가 설계대로 정확하게 동작하더라도 문제가 발생할 수 있다.

예를 들어 특정 사용자가 결제 없이 좌석을 계속 점유할 수 있다면, 다른 사용자는 해당 좌석을 예약하지 못하게 된다. 공격자가 이를 반복하면 영화관의 정상적인 운영까지 방해할 수 있다.

이처럼 Insecure Design은 기능이 정상적으로 동작하는지만으로는 판단하기 어려운 보안 문제이다.

핵심은 다음과 같다.

**시스템이 의도한 대로 동작한다는 사실이 시스템이 안전하다는 것을 의미하지는 않는다.**

### 3.2. Insecure Design과 Insecure Implementation의 차이

Insecure Design을 이해하기 위해서는 Insecure Implementation, 즉 안전하지 않은 구현과의 차이를 알아야 한다.

두 개념은 모두 보안 취약점을 발생시킬 수 있지만, 문제가 시작되는 지점이 다르다.

| 구분 | Insecure Design | Insecure Implementation |
|---|---|---|
| 문제 발생 단계 | 요구사항 및 설계 단계 | 코드 구현 단계 |
| 주요 원인 | 보안 규칙이나 보호 방법이 부족함 | 정해진 보안 규칙을 잘못 구현함 |
| 예시 | 비밀번호 재설정 요청 횟수에 제한을 두지 않음 | 설계된 요청 횟수 제한을 코드에서 잘못 구현함 |
| 해결 방법 | 요구사항 및 시스템 구조 재검토 | 코드 수정 및 구현 검증 |

은행의 계좌이체 기능을 예시로 생각해 보자.

은행에서 다음과 같은 규칙을 설계했다고 가정한다.

- 송금하려는 금액은 계좌 잔액을 초과할 수 없다.
- 송금하기 전 사용자의 본인 확인을 수행해야 한다.
- 일정 금액 이상의 송금에는 추가 인증이 필요하다.

이러한 규칙이 존재하지만 개발자가 잔액 검사 부분을 잘못 구현했다면, 이는 구현상의 문제에 해당한다.

반면, 처음부터 고액 송금에 대한 추가 인증이나 계좌 소유자 확인이 필요하다는 보안 요구사항을 고려하지 않았다면 설계상의 문제로 볼 수 있다.

물론 실제 취약점에서는 설계와 구현 문제가 함께 나타날 수도 있다.

중요한 점은 설계 단계에서 필요한 보호 장치를 고려하지 않았다면, 코드를 단순히 수정하는 것만으로 근본적인 문제를 해결하기 어려울 수 있다는 것이다.

## 4. Insecure Design은 왜 발생하는가?

### 4.1. 정상적인 사용자만을 가정한 설계

서비스를 개발할 때는 일반적으로 사용자가 기능을 정상적인 목적과 순서에 따라 이용할 것이라고 가정한다.

온라인 쇼핑몰의 구매 과정을 예로 들어 보자.

상품 선택 → 장바구니 담기 → 결제 → 주문 완료

일반적인 사용자는 위와 같은 순서로 서비스를 이용한다.

하지만 공격자는 반드시 이 순서를 따르지 않는다. 결제 단계를 건너뛰거나, 특정 요청을 여러 번 전송하거나, 정상적인 기능을 예상하지 못한 방식으로 조합할 수도 있다.

사용자가 서비스에서 제공하는 화면을 통해서만 기능을 사용할 것이라고 가정하면 이러한 행동을 놓치게 된다.

따라서 설계 단계에서는 정상적인 사용자의 행동뿐만 아니라 공격자가 어떤 방식으로 기능을 악용할 수 있는지도 고려해야 한다.

### 4.2. 비즈니스 로직에 대한 검증 부족

비즈니스 로직(Business Logic)은 서비스가 실제로 동작하기 위해 필요한 업무 규칙을 의미한다.

온라인 쇼핑몰이라면 다음과 같은 규칙들이 비즈니스 로직에 해당한다.

- 상품의 가격을 계산하는 방법
- 할인 쿠폰을 적용할 수 있는 조건
- 사용자의 결제가 완료되는 조건
- 재고가 부족할 때 주문을 제한하는 방법
- 환불을 허용하는 조건

이러한 규칙에 허점이 있다면 공격자가 시스템의 정상적인 기능을 이용하여 부당한 이익을 얻을 수 있다.

이를 Business Logic Vulnerability, 즉 비즈니스 로직 취약점이라고 한다.

비즈니스 로직 취약점이 모두 설계상의 문제인 것은 아니다. 적절하게 정의된 규칙을 구현하는 과정에서 오류가 발생할 수도 있다.

하지만 처음부터 잘못된 규칙을 정의하거나 필요한 검증 조건을 고려하지 않았다면 Insecure Design과 연결된다.

### 4.3. 클라이언트에 대한 과도한 신뢰

웹 애플리케이션은 일반적으로 사용자가 직접 이용하는 클라이언트와 실제 데이터를 처리하는 서버로 구성된다.

클라이언트는 사용자에게 화면을 보여주고 입력을 전달하는 역할을 하며, 서버는 요청을 처리하고 데이터베이스의 데이터를 조회하거나 수정한다.

예를 들어 쇼핑몰 화면에서 상품의 가격이 100,000원으로 표시된다고 가정해 보자.

개발자가 사용자는 화면에 표시된 가격을 변경할 수 없다고 생각하여 서버에서도 클라이언트가 전달한 가격을 그대로 사용한다면 문제가 발생할 수 있다.

공격자는 브라우저나 HTTP 요청을 분석하는 도구를 이용하여 서버로 전송되는 값을 변경할 수 있기 때문이다.

클라이언트에서 표시하거나 제한한 값은 그 자체로 신뢰할 수 있는 정보가 아니다.

상품 가격, 사용자 권한, 결제 금액과 같이 중요한 정보는 서버가 신뢰할 수 있는 데이터를 바탕으로 직접 확인해야 한다.

### 4.4. 보안을 개발 이후의 문제로 생각하는 경우

서비스 개발에서는 정해진 기간 안에 필요한 기능을 구현하는 일이 우선시되기 쉽다.

이 과정에서 보안 검토는 개발이 완료된 후 수행해야 하는 별도의 작업으로 취급되기도 한다.

그러나 이미 구현된 시스템에 근본적인 설계 문제가 존재한다면, 보안 기능을 추가하는 것만으로 해결되지 않을 수 있다.

예를 들어 서비스의 모든 기능이 사용자 간 데이터 격리를 고려하지 않고 설계되었다면, 개발이 완료된 후 이를 해결하기 위해 데이터베이스 구조와 권한 관리 방식 등을 함께 수정해야 할 수도 있다.

이 때문에 보안은 개발이 끝난 후 추가하는 기능이 아니라, 초기 요구사항과 설계 단계부터 고려해야 하는 요소이다.

## 5. Insecure Design의 공격 시나리오

Insecure Design이 실제로 어떤 문제를 발생시키는지 이해하기 위해 몇 가지 가상의 서비스 사례를 살펴보았다.

### 5.1. 계정 복구 기능의 설계 문제

첫 번째 사례는 비밀번호를 잊어버린 사용자를 위한 계정 복구 기능이다.

일부 서비스에서는 사용자의 신원을 확인하기 위해 다음과 같은 보안 질문을 사용한다.

- 태어난 지역은 어디인가?
- 처음 다닌 초등학교의 이름은 무엇인가?
- 반려동물의 이름은 무엇인가?

개발자는 이러한 질문의 답을 본인만 알고 있을 것이라고 가정했을 수 있다.

그러나 실제로는 SNS 게시물이나 주변 사람들을 통해 답을 알아낼 가능성이 있다.

공격 과정을 정리하면 다음과 같다.

1. 공격자가 피해자의 SNS 등 공개된 정보를 확인한다.
2. 피해자의 반려동물 이름이나 학교 이름을 알아낸다.
3. 서비스의 비밀번호 복구 기능을 이용한다.
4. 알아낸 정보를 보안 질문의 답으로 제출한다.
5. 서비스가 공격자를 계정 소유자로 판단하면 비밀번호 재설정이 가능해진다.

이 사례에서 시스템은 설계된 규칙에 따라 정상적으로 동작한다. 올바른 답을 입력한 사람에게 계정 복구를 허용했기 때문이다.

하지만 '정답을 알고 있는 사람은 반드시 계정 소유자이다'라는 가정 자체가 잘못되어 있다.

따라서 이 문제는 질문의 답을 확인하는 코드를 수정하는 것으로 해결되지 않는다. 계정 복구 방식 자체를 변경해야 한다.

개선 방법으로는 기존에 등록한 이메일을 통한 일회용 재설정 링크, 복구 코드 또는 적절한 추가 본인 확인 수단 등을 사용할 수 있다. 복구 요청에 대한 횟수 제한과 사용자 알림도 함께 고려해야 한다.

OWASP의 A06 공식 문서에서도 이러한 보안 질문을 이용한 계정 복구 방식을 안전하지 않은 설계의 사례로 설명하고 있다.

### 5.2. 영화관 좌석 대량 예약

두 번째 사례는 OWASP 공식 문서에 소개된 영화관 예약 시나리오이다.

영화관이 15명을 초과하는 단체 예약에 대해서는 보증금을 받도록 설계했다고 가정하자.

| 예약 인원 | 정책 |
|---|---|
| 15명 이하 | 보증금 없이 예약 |
| 15명 초과 | 보증금 지불 후 예약 |

이 정책은 대규모 예약으로 인한 피해를 줄이기 위해 만들어졌다.

하지만 하나의 예약 요청에 포함된 인원만 확인하고, 동일한 사용자가 여러 번 예약하는 상황은 고려하지 않았다면 어떻게 될까?

공격자는 한 번에 100석을 예약하는 대신 14석씩 나누어 반복적으로 예약할 수 있다.

각 요청은 정상적인 예약 조건을 충족하기 때문에 서버는 이를 허용한다.

결과적으로 공격자는 보증금을 내지 않고도 대량의 좌석을 점유할 수 있으며, 정상적인 고객은 영화관을 이용하지 못할 수 있다.

이 공격에서는 SQL Injection이나 악성 코드가 사용되지 않는다. 단순히 정상적인 예약 기능을 반복해서 사용했을 뿐이다.

문제는 대규모 예약을 제한하려는 정책이 개별 요청만을 기준으로 설계되었다는 것이다.

이를 개선하기 위해서는 사용자별 전체 예약 수, 미결제 좌석 수, 예약 요청 빈도, 좌석 점유 시간 등을 함께 고려해야 한다.

특히 결제가 완료되지 않은 예약은 일정 시간이 지나면 자동으로 해제되도록 설계할 필요가 있다.

이 사례를 통해 보안 설계에서는 한 번의 요청이 안전한지만 확인할 것이 아니라, 여러 요청이 결합되었을 때 어떤 결과가 발생하는지도 고려해야 한다는 것을 알 수 있다.

### 5.3. 온라인 쇼핑몰의 할인 쿠폰 중복 사용

세 번째 사례는 할인 쿠폰을 제공하는 온라인 쇼핑몰이다.

쇼핑몰이 신규 회원에게 10,000원 할인 쿠폰을 지급하며, 각 쿠폰은 한 번만 사용할 수 있도록 정책을 정했다고 가정해 보자.

쿠폰을 사용하는 과정은 다음과 같다.

1. 서버가 쿠폰의 사용 여부를 확인한다.
2. 사용하지 않은 쿠폰이라면 주문 금액을 할인한다.
3. 할인 처리가 끝나면 쿠폰을 사용 완료 상태로 변경한다.

순서대로 한 번씩 요청이 처리된다면 문제가 발생하지 않는다.

하지만 두 개의 요청이 거의 동시에 전달되면 상황이 달라질 수 있다.

| 시간 | 요청 A | 요청 B |
|---|---|---|
| T1 | 쿠폰 사용 여부 확인 | 쿠폰 사용 여부 확인 |
| T2 | 미사용 상태 확인 | 미사용 상태 확인 |
| T3 | 10,000원 할인 | 10,000원 할인 |
| T4 | 쿠폰 사용 완료 처리 | 쿠폰 사용 완료 처리 |

두 요청이 모두 쿠폰이 사용되지 않은 상태에서 확인을 완료하면 각각 할인을 적용할 수 있다.

결과적으로 한 번만 사용할 수 있어야 하는 쿠폰이 두 번 사용된다.

이러한 문제는 Race Condition(경쟁 상태)과 관련되어 있다.

Race Condition은 여러 작업이 동시에 진행될 때 작업의 실행 순서나 타이밍에 따라 결과가 달라지는 문제이다.

이 경우 쿠폰을 사용할 수 있는지 확인하는 작업과 사용 상태를 변경하는 작업이 하나의 안전한 연산으로 처리되지 않은 것이 원인이다.

이러한 동시 요청을 설계 단계에서 고려하지 않았다면 Insecure Design에 해당하는 문제로 볼 수 있다.

해결하기 위해서는 데이터베이스 트랜잭션과 잠금, 조건부 업데이트 등을 이용하여 쿠폰 상태 확인과 사용 처리가 안전하게 이루어지도록 해야 한다.

중요한 것은 동시에 여러 요청이 들어와도 '하나의 쿠폰은 한 번만 사용할 수 있다'라는 규칙이 반드시 유지되어야 한다는 점이다.

### 5.4. 온라인 쇼핑몰의 결제 단계 우회

이번에는 온라인 쇼핑몰의 주문 처리 과정을 생각해 보자.

정상적인 주문은 다음과 같은 순서로 진행된다.

장바구니 → 주문 생성 → 결제 완료 → 배송 준비

하지만 서버가 주문의 현재 상태를 확인하지 않고 배송 준비 요청을 처리한다면, 결제가 완료되지 않은 주문에 대해서도 배송 절차가 시작될 가능성이 있다.

개발자는 사용자가 쇼핑몰 화면에서 결제를 완료해야만 다음 단계로 이동할 수 있도록 구현했을 수 있다.

그러나 화면에서 다음 단계로 이동하지 못하게 하는 것과 서버에서 해당 요청을 처리하지 못하게 하는 것은 서로 다른 문제이다.

공격자가 직접 서버에 요청을 전달할 경우, 화면에서 설정한 제한을 따르지 않을 수 있기 때문이다.

따라서 서버는 배송 준비 요청을 받았을 때 다음과 같은 내용을 확인해야 한다.

- 실제로 존재하는 주문인가?
- 요청을 수행할 수 있는 권한이 있는가?
- 신뢰할 수 있는 결제 확인 절차를 거쳤는가?
- 현재 주문 상태에서 배송 준비 상태로 변경할 수 있는가?

이러한 검증 없이 기능을 제공한다면 결제 없이 상품을 배송받거나 주문 상태를 임의로 변경하는 문제가 발생할 수 있다.

## 6. Insecure Design을 간단한 코드로 이해하기

개념만으로는 이해하기 어려울 수 있으므로, 온라인 쇼핑몰의 결제 금액 계산 기능을 간단한 Python 코드로 표현해 보았다.

아래 코드는 실제 서비스의 취약점을 분석한 것이 아니라, 설계 문제를 설명하기 위해 구성한 교육용 예시이다.

### 6.1. 안전하지 않은 설계

```python
def calculate_price(request):
    price = request["price"]
    quantity = request["quantity"]

    if quantity <= 0:
        raise ValueError("Invalid quantity")

    return price * quantity
```

위 코드는 클라이언트로부터 상품 가격과 수량을 전달받아 전체 결제 금액을 계산한다.

상품 수량이 0 이하인 경우에는 오류를 발생시키므로 어느 정도의 입력값 검증도 수행한다.

정상적인 요청이 다음과 같다면,

```python
request = {
    "price": 100000,
    "quantity": 1
}

print(calculate_price(request))
```

결과는 다음과 같다.

```text
100000
```

하지만 클라이언트가 가격을 변경하여 전달할 경우에는 어떻게 될까?

```python
request = {
    "price": 100,
    "quantity": 1
}

print(calculate_price(request))
```

결과는 다음과 같다.

```text
100
```

원래 100,000원인 상품의 결제 금액이 100원으로 계산된다.

이 코드의 문제는 계산식이 잘못되었다는 것이 아니다. 가격과 수량을 곱하는 연산 자체는 정상적으로 이루어진다.

문제는 서버가 상품 가격을 어떤 정보로부터 결정해야 하는지에 대한 설계이다.

클라이언트가 전달한 가격을 신뢰하도록 설계했기 때문에, 공격자는 자신이 원하는 가격을 서버에 전달할 수 있다.

### 6.2. 개선된 설계

```python
PRODUCTS = {
    "product_001": 100000
}

def calculate_price(request):
    product_id = request["product_id"]
    quantity = request["quantity"]

    if product_id not in PRODUCTS:
        raise ValueError("Invalid product")

    if type(quantity) is not int:
        raise ValueError("Invalid quantity type")

    if quantity < 1 or quantity > 10:
        raise ValueError("Invalid quantity")

    price = PRODUCTS[product_id]

    return price * quantity
```

개선된 코드는 클라이언트가 전달한 가격을 사용하지 않는다.

대신 상품 ID를 전달받은 후 서버에 저장된 상품 정보를 조회하여 실제 가격을 계산한다.

```python
request = {
    "product_id": "product_001",
    "quantity": 1,
    "price": 100
}

print(calculate_price(request))
```

결과는 다음과 같다.

```text
100000
```

클라이언트가 가격을 100원으로 설정하더라도 서버는 자신이 관리하는 상품 가격을 기준으로 계산하므로 원래 가격인 100,000원이 반환된다.

두 코드의 차이는 다음과 같다.

| 구분 | 안전하지 않은 설계 | 개선된 설계 |
|---|---|---|
| 상품 가격 결정 | 클라이언트가 전달 | 서버가 직접 조회 |
| 상품 정보 확인 | 수행하지 않음 | 등록된 상품인지 확인 |
| 수량 검증 | 양수 여부 | 자료형 및 허용 범위 |
| 가격 조작 | 가능 | 예시의 가격 조작 방지 |

물론 실제 쇼핑몰에서는 재고 확인, 할인 정책, 결제 금액 검증, 동시 주문 처리 등도 추가로 고려해야 한다.

이 예시의 핵심은 단순히 입력값 검증 코드를 추가하는 것이 아니라, 어떤 정보를 신뢰할 것인지에 대한 설계 자체를 변경했다는 것이다.

## 7. Insecure Design을 예방하는 방법

### 7.1. Threat Modeling

Threat Modeling(위협 모델링)은 시스템에 어떤 보안 위협이 존재할 수 있는지 분석하고, 이에 대한 대응 방법을 설계하는 과정이다.

쉽게 설명하면 시스템을 개발하기 전에 공격자의 입장에서 발생할 수 있는 문제를 미리 생각해 보는 것이다.

OWASP의 Threat Modeling Cheat Sheet에서는 위협 모델링을 다음과 같은 네 가지 질문을 중심으로 설명한다.

1. 어떤 시스템을 만들고 있는가?
2. 어떤 문제가 발생할 수 있는가?
3. 그 문제에 어떻게 대응할 것인가?
4. 대응이 충분히 이루어졌는지 어떻게 확인할 것인가?

앞서 살펴본 영화관 예약 시스템에 적용해 보자.

먼저 시스템이 보호해야 할 자산을 확인한다.

- 영화관 좌석
- 고객의 개인정보
- 결제 정보
- 영화관의 정상적인 운영

이후 예상 가능한 위협을 생각해 본다.

| 예상 위협 | 대응 방안 |
|---|---|
| 한 사용자가 좌석을 대량 예약함 | 사용자별 예약 수 제한 |
| 결제 없이 좌석을 점유함 | 예약 만료 시간 설정 |
| 같은 좌석을 여러 명이 예약함 | 데이터베이스 제약조건 및 동시성 제어 |
| 자동화된 프로그램이 예약을 반복함 | 요청 횟수 제한 및 이상 행위 탐지 |
| 다른 사용자의 예약을 취소함 | 예약 소유자 및 요청 권한 확인 |

마지막으로 실제 테스트를 통해 각각의 대응 방안이 정상적으로 작동하는지 검증한다.

위협 모델링의 장점은 단순히 개발이 끝난 후 취약점을 찾는 것이 아니라, 개발 전에 필요한 보안 요구사항을 도출할 수 있다는 것이다.

### 7.2. Secure by Design

Secure by Design은 시스템을 설계하는 초기 단계부터 보안을 핵심 요소로 고려하는 접근 방식이다.

기존에는 기능을 먼저 개발한 후 보안 테스트를 수행하고 발견된 취약점을 수정하는 방식으로 개발이 진행되는 경우가 많았다.

하지만 Secure by Design에서는 기능의 요구사항을 정의하는 과정부터 보안 요구사항을 함께 고려한다.

예를 들어 회원가입 기능을 설계한다고 가정해 보자.

기능 요구사항은 다음과 같다.

- 사용자는 이메일을 이용하여 회원가입할 수 있다.
- 사용자는 비밀번호를 설정할 수 있다.
- 회원가입이 완료되면 로그인할 수 있다.

여기에 다음과 같은 보안 요구사항을 함께 고려해야 한다.

- 비밀번호는 안전한 비밀번호 해시 알고리즘을 이용하여 저장한다.
- 이메일의 소유 여부를 검증한다.
- 자동화된 대량 계정 생성을 제한한다.
- 사용자에게 불필요한 권한이 부여되지 않도록 한다.

즉, 어떤 기능을 만들 것인가뿐만 아니라 해당 기능이 어떤 조건에서 안전하게 동작해야 하는지까지 설계하는 것이다.

### 7.3. 비즈니스 로직의 상태 전이 정의

상태(State)는 시스템이나 데이터가 특정 시점에 어떤 상황에 있는지를 나타낸다.

상태 전이(State Transition)는 하나의 상태에서 다른 상태로 변경되는 것을 의미한다.

온라인 쇼핑몰의 주문 상태는 다음과 같이 표현할 수 있다.

```text
[주문 생성]
     |
     v
[결제 대기]
     |
     | 결제 확인
     v
[결제 완료]
     |
     v
[배송 준비]
     |
     v
[배송 완료]
```

이러한 구조에서 주문이 결제 대기 상태라면, 결제가 확인되기 전에는 배송 준비 상태로 변경되어서는 안 된다.

따라서 서버는 현재 상태와 다음 상태 사이의 변경이 허용되는지 검증해야 한다.

예를 들어 다음과 같은 상태 변경 규칙을 정의할 수 있다.

| 현재 상태 | 요청 상태 | 허용 여부 |
|---|---|---|
| 결제 대기 | 결제 완료 | 결제 확인 후 허용 |
| 결제 대기 | 배송 준비 | 거부 |
| 결제 완료 | 배송 준비 | 허용 |
| 배송 완료 | 결제 대기 | 거부 |

이처럼 각 기능의 상태와 허용되는 전이를 명확히 정의하면, 공격자가 처리 순서를 건너뛰거나 잘못된 상태 변경을 유도하는 문제를 줄일 수 있다.

물론 실제 서비스에서는 주문 취소, 환불, 배송 실패와 같은 추가적인 상태도 고려해야 한다.

### 7.4. 보안 불변조건 정의

불변조건(Invariant)은 시스템의 동작 과정에서 항상 만족해야 하는 조건을 의미한다.

예를 들어 은행 계좌 시스템에서는 다음과 같은 조건을 정의할 수 있다.

- 당좌대월이 허용되지 않는 계좌의 잔액은 음수가 될 수 없다.
- 계좌 소유자의 승인 없이 송금할 수 없다.
- 동일한 송금 요청이 중복으로 실행되지 않아야 한다.

온라인 쇼핑몰에서는 다음과 같은 조건을 정의할 수 있다.

- 한 번만 사용할 수 있는 쿠폰은 두 번 이상 사용할 수 없다.
- 결제되지 않은 주문은 배송되지 않아야 한다.
- 판매된 상품 수량이 실제 판매 가능한 재고를 초과해서는 안 된다.

이러한 조건을 설계 단계에서 명확하게 정의하면, 보안 테스트를 수행할 때 무엇을 확인해야 하는지 알 수 있다.

특히 시스템이 여러 작업을 동시에 처리하는 경우에는 각각의 기능이 정상적으로 동작하는 것뿐만 아니라, 여러 작업이 결합되었을 때도 불변조건이 유지되는지 확인해야 한다.

### 7.5. 악용 시나리오를 고려한 테스트

일반적인 기능 테스트는 사용자가 정상적인 방식으로 서비스를 이용했을 때 기능이 올바르게 동작하는지 확인한다.

예를 들어 로그인 기능의 경우 올바른 아이디와 비밀번호를 입력하면 로그인이 성공하는지 확인한다.

그러나 보안 테스트에서는 정상적인 사용 시나리오뿐만 아니라 악용 시나리오(Misuse Case)도 고려해야 한다.

| 기능 | 정상적인 테스트 | 보안 테스트 |
|---|---|---|
| 로그인 | 올바른 비밀번호로 로그인 | 반복적인 인증 시도 제한 확인 |
| 쿠폰 사용 | 쿠폰을 사용하면 할인 적용 | 동일 쿠폰의 동시 사용 시도 |
| 상품 구매 | 결제 후 주문 완료 | 결제 단계 생략 시도 |
| 좌석 예약 | 빈 좌석을 정상 예약 | 동일 좌석의 동시 예약 시도 |
| 계좌이체 | 정상 금액 송금 | 잔액을 초과하는 동시 송금 시도 |

이러한 테스트는 단순히 예상된 기능이 동작하는지 확인하는 것을 넘어, 설계 단계에서 정의한 보안 규칙이 실제로 지켜지고 있는지 확인하는 과정이다.

### 7.6. Secure SDLC와 ASVS 활용

SDLC(Software Development Life Cycle)는 소프트웨어를 개발하고 운영하는 전체 생명주기를 의미한다.

Secure SDLC는 이러한 개발 과정에 보안 활동을 포함시키는 방식이다.

| 개발 단계 | 보안 활동 |
|---|---|
| 요구사항 분석 | 보안 요구사항 정의 |
| 설계 | 위협 모델링 및 보안 설계 검토 |
| 구현 | 안전한 코딩 및 코드 리뷰 |
| 테스트 | 취약점 분석 및 악용 시나리오 검증 |
| 배포 | 안전한 설정 및 운영 환경 점검 |
| 운영 | 이상 행위 탐지 및 보안 문제 개선 |

이때 OWASP ASVS(Application Security Verification Standard)를 활용할 수 있다.

ASVS는 웹 애플리케이션의 보안 요구사항을 구체적으로 정의하고 검증하기 위한 표준이다.

예를 들어 ASVS 5.0.0에서는 비즈니스 로직의 처리 순서, 기능의 사용 제한, 트랜잭션의 일관성, 제한된 자원의 중복 사용 방지 등에 대한 요구사항을 제시한다.

OWASP Top 10이 어떤 보안 위험에 주의해야 하는지 알려주는 자료라면, ASVS는 시스템의 보안 수준을 확인하기 위해 어떤 요구사항을 검증해야 하는지 보다 구체적으로 알려주는 자료라고 이해할 수 있다.

## 8. Insecure Design은 어떻게 발견할 수 있을까?

Insecure Design의 어려운 점 중 하나는 일반적인 보안 검사 도구만으로 모든 문제를 발견하기 어렵다는 것이다.

SQL Injection과 같은 취약점은 특정한 입력에 대한 서버의 반응을 분석하여 발견할 수 있는 경우가 있다.

하지만 비즈니스 로직의 설계 문제를 발견하기 위해서는 해당 서비스가 어떤 규칙에 따라 동작해야 하는지 이해해야 한다.

예를 들어 어떤 쇼핑몰에서 쿠폰을 두 번 사용할 수 있다고 가정해 보자.

쿠폰의 중복 사용이 허용되는 서비스라면 문제가 아닐 수 있다. 반면 쿠폰을 한 번만 사용할 수 있도록 정책이 정해져 있다면 취약점이 될 수 있다.

동일한 시스템 동작도 서비스의 요구사항에 따라 보안 문제인지 아닌지가 달라질 수 있는 것이다.

따라서 Insecure Design을 분석하기 위해서는 다음과 같은 접근이 필요하다.

1. 서비스의 기능과 비즈니스 규칙을 이해한다.
2. 보호해야 할 자산과 반드시 지켜야 할 조건을 정의한다.
3. 사용자가 정상적인 처리 순서를 변경할 수 있는지 분석한다.
4. 동일한 요청을 반복하거나 동시에 수행했을 때 발생하는 결과를 확인한다.
5. 클라이언트가 전달하는 정보 중 서버가 신뢰하고 있는 데이터가 무엇인지 확인한다.
6. 발견된 문제가 실제 보안 위험으로 이어질 수 있는지 검증한다.

이러한 과정에서 자동화 도구도 활용할 수 있지만, 도구가 해당 서비스의 모든 업무 규칙을 이해하는 것은 아니다.

결국 보안 분석가가 시스템의 목적과 동작 방식을 이해하고, 개발자가 고려하지 않았던 상황을 찾아내는 능력이 중요하다.

PortSwigger의 Web Security Academy에서는 Business Logic Vulnerabilities와 관련한 실습 환경을 제공하고 있다. 이후 이러한 실습을 통해 실제 요청을 분석하고 비즈니스 로직 취약점을 발견하는 연습을 해보고 싶다.

## 9. 공부하면서 느낀 점

이번에 Insecure Design에 대해 공부하면서 보안 취약점을 바라보는 관점이 조금 달라졌다.

기존에는 보안 취약점이라고 하면 주로 코드에서 잘못된 부분을 찾아내고, 이를 이용하여 개발자가 의도하지 않은 동작을 발생시키는 것이라고 생각했다. 특히 포너블을 공부하면서 메모리 구조나 프로그램의 실행 과정에서 발생하는 오류에 집중했던 것 같다.

하지만 Insecure Design의 사례들을 살펴보면서 개발자가 의도한 대로 프로그램이 동작하더라도 그 의도 자체에 허점이 존재할 수 있다는 것을 알게 되었다.

영화관 예약이나 할인 쿠폰과 같은 사례가 특히 인상적이었다.

공격자가 특별히 복잡한 공격 기법을 사용하지 않아도, 정상적인 기능을 여러 번 반복하거나 서로 다른 요청을 동시에 실행하는 것만으로 보안 문제가 발생할 수 있었다.

이는 취약점을 찾기 위해 단순히 코드를 읽고 오류를 발견하는 능력뿐만 아니라, 시스템이 왜 이러한 방식으로 설계되었는지 이해하는 능력도 필요하다는 것을 보여준다.

또한 시스템의 기능을 분석할 때 '이 기능이 어떻게 동작하는가?'라는 질문에서 그치지 않고 다음과 같은 질문도 함께 던져야 한다고 느꼈다.

- 개발자는 어떤 사용자의 행동을 가정했을까?
- 공격자는 그 가정을 어떻게 벗어날 수 있을까?
- 여러 정상적인 기능을 조합했을 때 예상하지 못한 문제가 발생할 수 있을까?
- 어떤 상황에서도 반드시 유지되어야 하는 규칙은 무엇일까?

앞으로 웹 애플리케이션 보안을 공부할 때는 개별 취약점의 공격 원리를 이해하는 것뿐만 아니라 서비스의 전체적인 구조와 비즈니스 로직을 분석하는 능력도 함께 기르고 싶다.

특히 직접 간단한 서비스를 개발하고, 정상적인 사용자와 공격자의 관점에서 각각 기능을 분석해 보면 설계 단계에서 어떤 부분을 놓치기 쉬운지 더 구체적으로 이해할 수 있을 것 같다.

## 10. 마무리

Insecure Design은 시스템을 구현하는 코드뿐만 아니라, 시스템을 만들기 위해 정의한 규칙과 구조 자체에도 보안 문제가 존재할 수 있다는 것을 보여준다.

안전한 시스템을 개발하기 위해서는 다음과 같은 점을 고려해야 한다.

- 설계 단계부터 보안 요구사항을 정의한다.
- 정상적인 사용뿐만 아니라 악용 가능성도 고려한다.
- 서버에서 중요한 데이터와 상태를 검증한다.
- 여러 요청이 동시에 처리되는 상황을 고려한다.
- 보안 불변조건을 정의하고 테스트를 통해 검증한다.
- 위협 모델링을 통해 시스템의 위험을 지속적으로 분석한다.

이번 공부를 통해 가장 중요하게 느낀 점은 보안이 단순히 완성된 프로그램에서 취약점을 찾아 수정하는 과정만은 아니라는 것이다.

시스템이 어떤 조건에서 동작해야 하고, 어떤 상황에서는 동작해서는 안 되는지를 고민하는 것부터 보안이 시작된다고 생각한다.

결국 안전한 코드를 작성하는 것도 중요하지만, 그 코드가 따라야 할 안전한 규칙을 먼저 설계하는 것 역시 중요하다.
