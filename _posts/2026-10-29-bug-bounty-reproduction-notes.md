버그바운티에서 좋은 제보는 취약점 이름보다 **재현 가능한 사실과 정확한 영향 범위**가 선명하다. 아래는 실제 발견 사례가 아닌 제보 작성 틀이다. 프로그램별 정책이 우선이므로 테스트 전 범위, 금지 행위, 계정 사용 조건, 공개 시점을 읽어야 한다.

## 먼저 범위 확인

- 대상 도메인·앱·버전이 현재 프로그램의 허용 범위에 포함되는가?
- 자동화, 부하 테스트, 다른 사용자 데이터 접근이 제한되는가?
- 테스트 계정을 만들 수 있는가? 계정 간 검증이 필요하다면 **본인이 관리하는 계정만** 사용한다.
- 유사한 현상이 이미 제외 항목으로 명시되어 있는가?

정책이 모호하다면 무리해서 진행하지 않고 운영자가 제공한 문의 경로를 사용한다.

## 관찰과 해석 분리

| 기록할 것 | 예시 형식 |
| --- | --- |
| 전제 조건 | 계정 유형, 대상 기능, 테스트 시각 |
| 재현 단계 | 최소한의 요청과 클릭 순서 |
| 기대 동작 | 권한 검사가 적용된 결과 |
| 실제 동작 | 직접 확인한 응답 또는 화면 |
| 영향 | 본인 계정으로 검증된 범위에 한정 |

예를 들어 "다른 계정의 모든 자료를 볼 수 있다"는 주장과 "내가 만든 두 번째 테스트 계정의 특정 자료를 첫 번째 계정에서 조회할 수 있었다"는 관찰은 다르다. 제보에는 후자처럼 **검증된 범위**를 적고, 확장 가능성은 별도 가설로 표시한다.

## 증거를 안전하게 준비하기

요청·응답을 첨부할 때는 세션 쿠키, 토큰, 개인정보를 가린다. 스크린샷에는 필요한 부분만 남긴다. 재현 횟수는 정책과 안전성을 고려해 최소화하고, 서비스 상태를 바꾸는 작업은 피한다. 데이터가 우연히 노출되었다면 더 읽거나 내려받지 말고 프로그램의 절차에 따라 알린다.

## 제보 초안

```text
제목: [기능]에서 확인한 [구체적 권한/검증 문제]
대상: [허용 범위 내 자산]
전제 조건: [내가 관리하는 테스트 계정 등]
재현 단계: 1. ... 2. ... 3. ...
기대 결과: ...
관찰 결과: ...
검증한 영향: ...
미확인 사항: ...
증거: 민감정보를 제거한 요청/응답 또는 화면
```

제보 후에는 프로그램의 공개 정책을 따른다. 수정 전에 상세 내용을 외부에 게시하지 않는다.
