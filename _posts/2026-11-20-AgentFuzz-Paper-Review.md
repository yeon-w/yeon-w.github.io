## 1. 서론: 연구 배경과 문제의식

### 1.1 LLM 기반 에이전트의 발전과 보안 문제

최근 대규모 언어 모델(LLM)은 단순히 질문에 답변하거나 텍스트를 생성하는 기능을 넘어, 외부 도구를 호출하고 실제 작업을 수행하는 에이전트(Agent) 형태로 발전하고 있다.

예를 들어 LLM 기반 에이전트는 사용자의 자연어 요청을 분석하여 파일을 읽거나, 데이터베이스에 접근하거나, 코드를 실행할 수 있다. 이러한 기능은 사용자의 작업을 자동화한다는 장점이 있지만, 동시에 에이전트가 수행하는 작업에 보안상 위험이 발생할 가능성도 높인다.

기존 LLM에서는 악의적인 프롬프트가 모델의 답변을 왜곡하는 문제가 주로 논의되었다. 그러나 LLM 기반 에이전트에서는 잘못된 프롬프트 처리 결과가 실제 시스템의 민감한 작업으로 연결될 수 있다.

특히 사용자 입력이 적절한 검증 없이 보안에 민감한 함수에 전달되면 코드 실행이나 SQL Injection과 같은 기존 소프트웨어 취약점이 발생할 수 있다.

### 1.2 Taint-style Vulnerability란?

Taint-style Vulnerability는 신뢰할 수 없는 외부 입력이 적절한 검증 없이 보안에 민감한 연산에 도달하여 발생하는 취약점을 의미한다.

일반적으로 다음 두 개념을 사용한다.

- **Source:** 사용자 입력과 같이 신뢰할 수 없는 데이터가 시스템에 들어오는 지점
- **Sink:** `eval()`, `exec()` 또는 SQL 실행 함수처럼 악의적인 데이터가 전달될 경우 보안 문제가 발생할 수 있는 지점

전통적인 웹 애플리케이션에서는 사용자 입력이 직접 Sink로 전달되는 과정에서 취약점이 발생할 수 있다.

반면 LLM 기반 에이전트에서는 사용자 입력이 LLM을 거쳐 해석되고, LLM의 응답에 따라 도구가 선택되며, 그 도구의 인자로 입력 데이터가 전달된다.

즉, 다음과 같은 데이터 흐름이 만들어진다.

**사용자 프롬프트 → LLM의 해석 및 응답 → 도구 선택 및 인자 생성 → 보안 민감 함수 실행**

이러한 구조에서는 기존의 정적 분석만으로 어떤 사용자 입력이 실제 위험한 함수에 전달되는지 판단하기 어렵다.

### 1.3 기존 연구의 한계

기존 연구인 LLMSmith는 LLM 통합 애플리케이션의 원격 코드 실행 취약점을 탐지하기 위해 정적 분석을 활용하였다.

정적 분석은 소스코드를 실행하지 않고 함수 호출 관계나 데이터 흐름을 분석할 수 있다는 장점이 있다. 그러나 LLM 에이전트에서는 다음과 같은 한계가 발생한다.

첫째, **동적 함수 호출을 정확하게 분석하기 어렵다.** Python 기반 에이전트는 LLM의 응답에 따라 실행할 도구를 결정한다. 따라서 정적 호출 그래프만으로 실제 호출 관계를 정확하게 재구성하기 어렵다.

둘째, **잠재적인 취약점과 실제 공격 가능한 취약점을 구분하기 어렵다.** 코드상으로 Source에서 Sink까지 경로가 존재하더라도 실제 실행에서는 조건문이나 입력 검증 때문에 해당 경로에 도달하지 못할 수 있다.

셋째, **자연어 입력의 의미를 고려하지 못한다.** 에이전트는 입력 프롬프트의 의미에 따라 실행하는 기능이 달라지므로 단순히 무작위 문자열을 생성하는 방식만으로는 원하는 코드 경로를 실행하기 어렵다.

이러한 문제를 해결하기 위해 저자들은 LLM 기반 에이전트에 적합한 새로운 퍼징 기법이 필요하다고 판단하였다.

## 2. 문제 정의와 연구 목표

본 논문은 **LLM 기반 에이전트에서 사용자 입력이 보안에 민감한 함수까지 전달되어 발생하는 Taint-style Vulnerability를 자동으로 탐지하는 것**을 목표로 한다.

기존 Directed Greybox Fuzzing은 특정 코드 위치에 도달하도록 입력을 생성하고 변형하는 방식이다. 그러나 LLM 에이전트는 자연어 입력을 기반으로 실행 경로를 결정하기 때문에 기존 방식을 그대로 적용하기 어렵다.

저자들은 이를 해결하기 위해 세 가지 연구 문제를 제시하였다.

**첫 번째 문제는 목표 기능을 실행할 수 있는 자연어 입력을 어떻게 생성할 것인가이다.**

일반적인 퍼저는 바이트나 구조화된 데이터를 변형하지만, 에이전트에서는 프롬프트의 의미가 실행할 도구를 결정한다. 따라서 특정 기능을 실행하도록 유도하는 자연어 Seed가 필요하다.

**두 번째 문제는 어떤 Seed가 취약점에 도달할 가능성이 높은지 어떻게 판단할 것인가이다.**

전통적인 거리 기반 퍼징은 목표 코드까지의 거리를 사용하지만, 에이전트에서는 동일한 거리에 위치한 실행 경로라도 자연어 의미에 따라 실제 도구 호출 가능성이 달라진다.

**세 번째 문제는 Seed를 어떻게 변형하여 취약점을 발생시킬 것인가이다.**

프롬프트는 목표 도구를 실행할 수 있어야 할 뿐만 아니라, 해당 도구 내부의 조건문을 만족하는 인자도 전달해야 한다.

저자들은 이 세 문제를 해결하기 위해 AgentFuzz를 제안하였다.

## 3. 핵심 아이디어: AgentFuzz

AgentFuzz는 LLM을 활용하여 자연어 입력을 생성하고, 실제 실행 결과를 피드백으로 활용하여 취약점이 발생할 가능성이 높은 입력을 반복적으로 탐색하는 **Directed Greybox Fuzzing 프레임워크**이다.

기존 퍼징과의 가장 큰 차이는 입력의 바이트 구조뿐 아니라 **자연어의 의미와 프로그램의 실행 경로를 함께 고려한다는 점**이다.

AgentFuzz는 크게 세 단계로 구성된다.

### 3.1 LLM-assisted Seed Generation

첫 번째 단계는 취약점을 발생시킬 가능성이 있는 초기 프롬프트를 생성하는 것이다.

AgentFuzz는 먼저 CodeQL 기반 정적 분석을 통해 `eval()`과 같은 Sink를 탐색하고, 해당 함수에 도달할 수 있는 호출 경로를 추출한다.

이때 함수명과 클래스명에는 해당 기능의 의미가 포함되어 있는 경우가 많다.

예를 들어 `ElasticsearchPermissionCheck.similarity_search`라는 메서드가 존재한다면, 이름만으로도 Elasticsearch를 이용하여 권한을 확인하며 유사도 검색을 수행하는 기능이라고 추론할 수 있다.

AgentFuzz는 이러한 정보를 LLM에 제공하고, 해당 기능을 호출할 수 있는 자연어 프롬프트를 생성하도록 한다.

단순히 무작위 프롬프트를 생성하는 것이 아니라, **목표 함수의 기능을 먼저 추론하고 그 기능을 실행하도록 요청하는 프롬프트를 생성한다는 점**이 핵심이다.

### 3.2 Feedback-driven Seed Scheduling

두 번째 단계는 생성된 여러 Seed 중에서 어떤 Seed를 우선적으로 변형할지 결정하는 것이다.

AgentFuzz는 입력을 실제 에이전트에서 실행하고, 실행 결과를 바탕으로 세 가지 요소를 평가한다.

- **Semantic Score:** 프롬프트가 실행한 기능의 의미와 목표 함수의 의미가 얼마나 유사한가?
- **Distance Score:** 실제 실행 경로가 목표 Sink에 얼마나 가까워졌는가?
- **Penalty Score:** 특정 Seed나 호출 경로가 과도하게 반복 선택되고 있지는 않은가?

이를 다음과 같은 수식으로 계산한다.

**Feedback Score = α × Semantic Score + β × Distance Score − Penalty Score**

예를 들어 단순히 문서를 검색하라는 프롬프트와 권한을 확인하면서 문서를 검색하라는 프롬프트가 있다고 가정하자.

목표 함수가 권한 확인 기능을 포함한다면 두 번째 프롬프트가 목표 함수의 의미와 더 가깝다.

실행 경로의 거리만 고려하면 이러한 차이를 발견하지 못할 수 있지만, AgentFuzz는 의미적 유사성을 함께 평가하여 더 유망한 Seed를 선택할 수 있다.

또한 동일한 Seed를 반복적으로 선택하는 현상을 방지하기 위해 Penalty Score를 사용한다.

### 3.3 Sink-guided Seed Mutation

세 번째 단계는 선택한 Seed를 변형하여 실제 취약점을 발생시키는 것이다.

AgentFuzz는 두 종류의 Mutator를 사용한다.

**① Functionality Mutator**

프롬프트가 목표 도구를 호출하지 못하는 경우 사용한다.

LLM은 기존 프롬프트의 의미와 실제 실행 경로를 분석하고, 목표 기능을 호출할 수 있도록 프롬프트를 수정한다.

예를 들어 일반적인 검색 도구가 실행되었다면, 권한 확인 기능이 포함된 검색 도구가 실행되도록 프롬프트의 표현을 변경한다.

이 과정에서는 이전 변형 결과와 피드백도 활용하여 동일한 실패를 반복하지 않도록 한다.

**② Argument Mutator**

목표 도구가 실행되었지만 내부 조건문을 만족하지 못하는 경우 사용한다.

이때 AgentFuzz는 Concolic Execution을 활용한다. Concolic Execution은 실제 실행값을 사용하면서 동시에 기호적으로 조건을 추적하여, 특정 코드 경로를 통과하는 데 필요한 입력 조건을 계산하는 방식이다.

AgentFuzz는 Z3 Solver를 사용하여 조건을 만족하는 인자 값을 구하고, 이를 원래 프롬프트에 반영한다.

예를 들어 목표 함수가 인자에 `source_doc:` 문자열이 포함되어야 실행된다면, 해당 조건을 만족하는 데이터가 도구에 전달되도록 프롬프트를 수정할 수 있다.

이때 Longest Common Substring Matching을 이용해 도구 인자와 원래 프롬프트의 대응 부분을 찾아 변형한다.

**결국 Functionality Mutator는 올바른 함수를 실행하도록 하고, Argument Mutator는 해당 함수 내부의 실행 조건을 만족하도록 만드는 역할을 한다.**

AgentFuzz는 실행 결과에 따라 적합한 Mutator를 선택하며, 최종적으로 공격용 입력이 Sink까지 전달되는지를 Bug Oracle로 검증한다.

## 4. 실험 및 평가

저자들은 AgentFuzz의 효과를 검증하기 위해 실제 오픈소스 LLM 에이전트 20개를 대상으로 실험을 수행하였다.

평가 대상에는 AutoGPT, LangFlow, DB-GPT, TaskWeaver, AgentScope 등이 포함되었다.

실험에서 AgentFuzz와 대상 에이전트의 기반 모델로 GPT-4o를 사용했으며, 각 Sink 위치에 대한 퍼징 제한 시간은 5분으로 설정하였다.

### 4.1 취약점 탐지 결과

AgentFuzz는 총 828개의 Sink 호출 지점을 식별하였으며, 실제로 34개의 새로운 취약점을 발견하였다.

발견한 취약점은 코드 인젝션, 명령어 인젝션, SQL Injection, SSTI 등으로 구성되었으며, 14개 오픈소스 에이전트에서 확인되었다.

논문의 주요 결과는 다음과 같다.

| 평가 항목 | 결과 |
|---|---:|
| 평가 대상 에이전트 | 20개 |
| 식별한 Sink 호출 지점 | 828개 |
| 발견한 취약점 | 34개 |
| 취약점이 발견된 에이전트 | 14개 |
| 검증된 탐지 결과의 Precision | 100% |
| 논문 요약 및 표에 기재된 CVE | 23개 |
| 전체 퍼징 CPU 시간 | 69.01시간 |
| 취약점 발견 평균 TTE | 약 121.8분 |

특히 발견한 34개의 취약점은 수동 검증을 통해 모두 실제 악용 가능한 것으로 확인되었다.

이는 AgentFuzz가 단순히 코드상으로 위험해 보이는 경로를 탐지하는 것을 넘어 실제 취약점을 유발하는 입력을 찾아낼 수 있음을 보여준다.

### 4.2 기존 연구 LLMSmith와의 비교

저자들은 기존 연구인 LLMSmith와 AgentFuzz를 비교하였다.

| 평가 지표 | LLMSmith | AgentFuzz |
|---|---:|---:|
| True Positive | 10 | 34 |
| False Positive | 332 | 0 |
| False Negative | 25 | 1 |
| Precision | 2.92% | 100% |
| Recall | 28.57% | 97.14% |

AgentFuzz는 LLMSmith보다 더 많은 취약점을 발견하면서도 오탐을 크게 감소시켰다.

이러한 성능 차이는 단순한 정적 분석 결과에 의존하지 않고, 실제 에이전트 실행을 통해 입력이 위험한 함수에 전달되는지 확인하기 때문이다.

또한 기존 정적 분석에서 놓치기 쉬운 동적 도구 호출 관계도 실제 실행을 통해 탐색할 수 있었다.

다만 여기서 제시한 Recall 97.14%는 **두 도구의 발견 결과 등을 기반으로 구성한 35개 취약점 정답 집합에 대한 수치**이다. 전체 프로그램에 존재하는 모든 취약점에 대한 탐지율이라고 해석해서는 안 된다.

### 4.3 Ablation Study

저자들은 AgentFuzz의 각 구성 요소가 탐지 성능에 실제로 기여하는지 확인하기 위해 Ablation Study를 수행하였다.

| 실험 구성 | 탐지 취약점 | Recall |
|---|---:|---:|
| 전체 AgentFuzz | 34 | 97.14% |
| Seed Generation 제거 | 19 | 54.29% |
| Seed Scheduling 제거 | 26 | 74.29% |
| Semantic Score 제거 | 27 | 77.14% |
| Mutator 제거 | 25 | 71.43% |

가장 큰 성능 저하는 Seed Generation을 제거했을 때 발생하였다.

이는 에이전트 퍼징에서 목표 기능을 실행할 수 있는 초기 자연어 입력을 생성하는 과정이 매우 중요하다는 것을 보여준다.

Semantic Score를 제거했을 때도 탐지 성능이 감소하였다. 이는 단순히 목표 코드까지의 거리만으로 Seed의 품질을 평가하는 것이 충분하지 않으며, 자연어 의미를 고려하는 과정이 실제 탐지 성능 향상에 기여한다는 것을 의미한다.

따라서 이 실험은 AgentFuzz의 성능이 단순히 LLM을 사용했다는 사실 때문이 아니라, 의미 기반 Seed 생성과 실행 피드백, 입력 변형을 결합한 설계에서 나온다는 점을 뒷받침한다.

## 5. 한계점 및 아쉬운 점

### 5.1 단일 프롬프트 기반 취약점 탐지에 한정됨

AgentFuzz는 하나의 프롬프트로 발생시킬 수 있는 Taint-style Vulnerability를 대상으로 한다.

그러나 실제 에이전트에서는 여러 단계의 상호작용이나 이전 작업의 상태가 이후 행동에 영향을 줄 수 있다.

예를 들어 첫 번째 요청으로 데이터를 저장하고, 두 번째 요청으로 특정 기능을 호출하며, 세 번째 요청에서 저장된 데이터가 위험한 함수에 전달되는 취약점은 단일 프롬프트 기반 탐지 방식으로 발견하기 어렵다.

따라서 여러 프롬프트와 상태 변화를 고려하는 확장이 필요하다.

### 5.2 사전에 정의된 Sink에 의존함

AgentFuzz는 미리 정의한 보안 민감 함수를 기준으로 취약점을 탐색한다.

따라서 Sink 목록에 존재하지 않는 위험한 함수나 새로운 형태의 보안 문제는 탐지하지 못할 수 있다.

또한 특정 Sink에 도달하는 취약점을 중심으로 설계되어 있기 때문에 권한 없는 작업 수행이나 비정상적인 에이전트 행동 등 모든 종류의 보안 위협을 탐지하는 범용 프레임워크라고 보기는 어렵다.

### 5.3 LLM 모델과 실행 환경에 대한 의존성

실험은 GPT-4o를 기반으로 수행되었기 때문에 다른 LLM을 사용하는 경우에도 동일한 성능이 나타나는지는 추가 검증이 필요하다.

특히 모델마다 자연어 해석, 도구 선택, 입력 검증 방식이 다를 수 있다.

또한 실험에서는 대상 에이전트에 대한 수동 계측과 웹 API 설정이 필요하였다. 따라서 새로운 에이전트에 적용할 때 추가적인 환경 구성 작업이 발생할 수 있다는 점도 한계로 볼 수 있다.

### 5.4 완전한 탐지율 검증의 어려움

AgentFuzz의 Precision은 발견한 34개의 취약점이 모두 실제 취약점이었다는 사실을 기반으로 한다.

그러나 탐지하지 못한 취약점이 얼마나 존재하는지는 완전히 확인되지 않았다.

저자들은 탐지되지 않은 Sink 중 일부를 표본으로 선택해 분석했지만 전체 Sink에 대한 완전한 정답 집합을 구축하지는 못했다.

따라서 논문의 높은 Recall 수치는 제한된 비교 집합에서 측정된 결과이며, 모든 미지의 취약점을 탐지할 수 있다는 의미는 아니다.

이러한 점을 고려하면 AgentFuzz의 강점은 완전한 취약점 탐지보다는 **탐지 결과의 정확성과 실제 취약점 재현 능력**에 있다고 판단된다.

## 6. 내가 생각하는 후속 연구 방향

### 6.1 Multi-step Agent Fuzzing으로의 확장

가장 먼저 확장해 보고 싶은 방향은 여러 단계의 프롬프트와 에이전트의 상태 변화를 고려하는 퍼징이다.

AgentFuzz는 개별 프롬프트가 특정 Sink에 도달하는지 확인한다. 그러나 실제 에이전트는 이전에 수행한 작업과 저장된 정보를 바탕으로 다음 행동을 결정하기도 한다.

따라서 후속 연구에서는 단일 Seed가 아니라 여러 프롬프트로 구성된 시퀀스를 입력으로 사용하고, 각 단계에서 에이전트의 상태와 도구 실행 결과를 관찰하도록 확장할 수 있을 것이다.

이를 통해 단일 입력에서는 나타나지 않지만 특정 작업 순서에서 발생하는 취약점을 탐지할 수 있을 것으로 기대한다.

### 6.2 보안 불변조건을 활용한 탐지

또 다른 방향은 사전에 정의된 Sink뿐 아니라 에이전트가 반드시 지켜야 하는 보안 속성을 기준으로 퍼징하는 것이다.

예를 들어 에이전트가 허가되지 않은 파일을 변경해서는 안 된다는 조건이나, 낮은 신뢰도의 입력이 높은 권한의 작업을 직접 결정해서는 안 된다는 조건을 정의할 수 있다.

이후 입력과 실행 시퀀스를 변형하면서 해당 조건이 위반되는지 확인하는 방식이다.

이러한 접근은 특정 위험 함수의 실행 여부에 집중하는 AgentFuzz의 탐지 범위를 확장하는 데 도움이 될 수 있다고 생각한다.

### 6.3 다양한 LLM 및 에이전트 환경에서의 재현성 검증

마지막으로 동일한 취약점과 퍼징 설정을 서로 다른 LLM 및 에이전트 환경에 적용하여 결과를 비교하는 연구도 의미가 있을 것이다.

모델에 따라 목표 도구 호출 성공률이나 프롬프트 해석 결과가 달라질 수 있으므로, 취약점 발견 여부뿐 아니라 반복 실행 시 성공률과 실행 비용도 함께 평가할 필요가 있다.

이를 통해 AgentFuzz의 성능이 특정 모델에 의존하는지, 어떤 요소가 탐지 안정성에 영향을 미치는지 분석할 수 있을 것이다.

## 7. 결론 및 느낀 점

이 논문을 읽으며 가장 인상적이었던 점은 전통적인 퍼징의 개념을 LLM 에이전트의 특성에 맞게 확장했다는 것이다.

기존 퍼징은 주로 바이트 단위의 입력 변형이나 실행 경로를 기준으로 탐색하지만, LLM 에이전트에서는 자연어 입력의 의미 자체가 프로그램의 실행 경로를 결정한다. 저자들은 이러한 차이를 단순히 퍼징의 장애물로 취급하지 않고, LLM을 활용한 Seed 생성과 의미 기반 피드백이라는 새로운 탐색 방법으로 연결하였다.

특히 Functionality Mutator와 Argument Mutator를 구분한 설계가 흥미로웠다. 단순히 취약한 코드에 가까이 도달하는 것과 실제로 그 코드를 실행하기 위한 조건을 만족하는 것은 서로 다른 문제이며, 두 과정을 분리하여 해결했다는 점에서 설계의 타당성을 확인할 수 있었다.

또한 이 논문은 LLM 에이전트의 보안 문제를 프롬프트 인젝션이나 탈옥 문제만으로 바라보아서는 안 된다는 점을 보여준다. LLM이 악의적인 요청을 수행하도록 유도되는 과정도 중요하지만, 궁극적으로 보안 문제가 발생하는 원인은 신뢰할 수 없는 데이터가 충분한 검증 없이 위험한 시스템 기능에 전달되는 구조일 수 있다.

다만 현재 방식은 단일 프롬프트로 특정 Sink를 실행시키는 취약점에 집중한다는 한계가 있다. 실제 에이전트는 여러 도구와 상태를 활용해 복잡한 작업을 수행하므로, 앞으로는 실행 순서와 상태 변화까지 고려한 탐지 방식이 중요해질 것으로 생각한다.

결과적으로 AgentFuzz는 **기존 소프트웨어 보안 분석 기법과 LLM의 자연어 이해 능력을 결합하여, LLM 에이전트의 실제 취약점을 자동으로 탐지할 수 있음을 보여준 연구**라고 정리할 수 있다.

이번 논문을 통해 새로운 AI 시스템의 보안 문제를 연구할 때 기존 보안 기법을 그대로 적용하는 데 그치지 않고, 시스템의 동작 특성에 맞게 분석 대상과 피드백 구조를 재설계하는 것이 중요하다는 점을 배울 수 있었다.
