# Fuzzing의 종류와 주요 Fuzzer 비교

## 1. 들어가며

소프트웨어의 취약점을 발견하는 방법에는 소스코드 분석, 정적 분석, 동적 분석 등 다양한 방법이 있다. 그중 **Fuzzing(퍼징)**은 프로그램에 다양한 입력값을 자동으로 전달하고, 실행 과정에서 발생하는 비정상적인 동작을 관찰하여 버그나 보안 취약점을 탐색하는 기법이다.

일반적인 소프트웨어 테스트는 개발자가 예상한 입력과 결과를 기반으로 수행되는 경우가 많다. 반면 퍼징은 개발자가 미처 예상하지 못한 비정상적인 입력이나 극단적인 입력을 통해 프로그램이 어떻게 동작하는지 확인한다.

이번 글에서는 퍼징의 기본 원리와 종류를 알아보고, AFL++, Jackalope, libFuzzer, Honggfuzz 등의 퍼저를 비교하여 각각 어떤 환경에서 활용할 수 있는지 정리해 보려고 한다.

---

## 2. Fuzzing이란?

### 2.1. Fuzzing의 개념

Fuzzing은 프로그램에 대량의 입력 데이터를 자동으로 생성하거나 변형하여 전달하고, 그 결과를 분석하여 버그 및 취약점을 발견하는 자동화된 소프트웨어 테스트 기법이다.

예를 들어 이미지 파일을 처리하는 프로그램이 있다고 가정해 보자.

정상적인 테스트에서는 올바른 이미지 파일을 입력하여 프로그램이 정상적으로 이미지를 처리하는지 확인한다.

하지만 퍼징에서는 다음과 같은 입력을 전달할 수 있다.

- 파일 헤더의 일부를 무작위로 변경한 이미지
- 파일 크기 정보와 실제 데이터 길이가 일치하지 않는 이미지
- 예상보다 훨씬 큰 값을 포함하는 이미지
- 일부 데이터가 누락되거나 반복된 이미지

이러한 입력을 처리하는 과정에서 프로그램이 비정상적으로 종료되거나, 허용되지 않은 메모리에 접근하거나, 지나치게 많은 자원을 사용할 수 있다.

퍼징은 이러한 비정상적인 동작을 자동으로 발견하는 것을 목표로 한다.

### 2.2. Fuzzing의 동작 과정

일반적인 퍼징은 다음 과정으로 이루어진다.

```text
[초기 입력 데이터(Seed)]
          |
          v
[입력 생성 또는 변형(Mutation)]
          |
          v
[테스트 대상 실행(Target)]
          |
          v
[실행 결과 및 피드백 수집]
          |
          v
[오류 또는 새로운 실행 경로 발견?]
          |
     +----+----+
     |         |
    Yes        No
     |         |
     v         |
[입력 저장]     |
     |         |
     +----+----+
          |
          v
    [다음 입력 생성]
          |
          └── 반복
```

먼저 퍼저는 초기 입력인 Seed를 기반으로 새로운 테스트 입력을 생성한다.

생성된 입력을 프로그램에 전달한 뒤 실행 결과를 확인한다. 이때 프로그램의 충돌(Crash), 실행 시간 초과(Timeout), 메모리 오류뿐 아니라 코드 커버리지와 같은 실행 정보도 수집할 수 있다.

특히 코드 커버리지 기반 퍼저는 기존에 실행되지 않았던 새로운 코드 경로를 발견한 입력을 저장하고, 이를 다시 변형하여 더욱 다양한 경로를 탐색한다.

이러한 과정을 반복하면서 자동으로 버그를 탐색한다.

### 2.3. Fuzzing의 주요 구성 요소

| 구성 요소 | 설명 |
|---|---|
| Seed | 퍼징을 시작할 때 사용하는 초기 입력 데이터 |
| Corpus | 퍼저가 관리하는 테스트 입력 집합 |
| Mutation | 기존 입력의 일부를 변경하여 새로운 입력을 생성하는 과정 |
| Harness | 퍼저가 생성한 입력을 테스트 대상에 전달하는 코드 |
| Coverage | 테스트 입력에 의해 실행된 코드의 범위 |
| Feedback | 이후 테스트 입력을 선택하거나 생성하는 데 사용하는 실행 정보 |
| Oracle | 프로그램의 실행 결과가 정상인지 오류인지 판단하는 기준 |
| Sanitizer | 메모리 오류 등 특정 문제를 탐지하도록 도와주는 도구 |

여기서 가장 중요한 개념은 **Harness와 Feedback**이라고 생각한다.

Harness는 퍼저와 테스트 대상을 연결하는 역할을 한다. 아무리 성능이 좋은 퍼저를 사용하더라도 Harness가 중요한 기능을 실행하지 못하면 해당 기능의 취약점을 발견하기 어렵다.

Feedback은 퍼저가 무작위 입력 생성에서 벗어나, 이전 실행 결과를 활용해 다음 입력을 선택할 수 있게 한다.

따라서 효과적인 퍼징을 위해서는 단순히 많은 입력을 생성하는 것뿐 아니라, 어떤 부분을 테스트하고 실행 결과를 어떻게 활용할 것인지도 중요하다.

## 3. Fuzzing의 종류

퍼징은 여러 기준에 따라 분류할 수 있다. 대표적으로 프로그램 내부 정보의 활용 정도, 입력 생성 방식, 피드백 활용 여부에 따라 구분할 수 있다.

### 3.1. 프로그램 내부 정보 활용 정도에 따른 분류

#### (1) Black-box Fuzzing

Black-box Fuzzing은 프로그램 내부의 코드 구조나 실행 경로 정보를 활용하지 않고, 입력과 출력 등의 외부 동작을 기반으로 테스트하는 방식이다.

프로그램에 데이터를 전달한 뒤 충돌이 발생했는지, 정상적으로 응답하는지 등을 확인한다.

**장점**
- 소스코드가 없어도 테스트할 수 있다.
- 내부 구현을 이해하지 않아도 테스트를 시작할 수 있다.
- 외부에서 접근 가능한 인터페이스를 대상으로 활용할 수 있다.

**단점**
- 어떤 코드 경로가 실행되었는지 파악하기 어렵다.
- 동일한 경로를 반복해서 테스트할 수 있다.
- 복잡한 조건문 내부의 취약점에 도달하기 어려울 수 있다.

예를 들어 네트워크 서버에 다양한 요청을 보내고 응답과 충돌 여부만 확인하는 테스트가 이에 해당할 수 있다.

#### (2) White-box Fuzzing

White-box Fuzzing은 프로그램의 내부 구조와 실행 조건을 분석하여 테스트 입력을 생성하는 방식이다.

대표적으로 Symbolic Execution(기호 실행)과 같은 기법을 활용할 수 있다.

기호 실행에서는 입력값을 구체적인 숫자가 아닌 기호로 표현하고, 특정 실행 경로에 도달하기 위한 조건을 수집한다.

예를 들어 다음과 같은 코드가 있다고 가정해 보자.

```c
if (a == 100 && b == 200) {
    // 특정 기능 실행
}
```

White-box 방식에서는 해당 코드 경로에 도달하기 위한 조건이 `a == 100` 및 `b == 200`이라는 사실을 분석하고, 이를 만족하는 입력을 생성할 수 있다.

**장점**
- 복잡한 분기 조건을 분석할 수 있다.
- 특정 실행 경로에 도달하기 위한 입력을 생성할 수 있다.

**단점**
- 분석에 필요한 연산 비용이 크다.
- 프로그램이 복잡해질수록 탐색해야 할 경로가 급격히 증가할 수 있다.
- 실제 프로그램 전체에 적용하기 어려운 경우가 있다.

#### (3) Grey-box Fuzzing

Grey-box Fuzzing은 Black-box와 White-box의 중간 형태로, 프로그램 내부의 일부 실행 정보를 활용하는 방식이다.

대표적으로 코드 커버리지 정보를 이용한다.

퍼저는 어떤 입력이 새로운 실행 경로를 발견했는지 확인하고, 해당 입력을 우선적으로 변형하여 테스트한다.

```text
입력 A → 기존에 실행했던 경로
입력 B → 새로운 분기 발견
입력 C → 기존에 실행했던 경로
```

이 경우 입력 B는 새로운 경로를 발견했기 때문에 이후 입력 생성에 활용될 가능성이 높다.

**장점**
- 완전한 White-box 분석보다 비교적 적은 비용으로 실행 경로를 탐색할 수 있다.
- 무작위 입력에만 의존하는 방식보다 효율적인 탐색이 가능하다.
- 실제 소프트웨어 보안 테스트에서 널리 활용된다.

**단점**
- 커버리지 정보만으로 프로그램의 모든 오류를 발견할 수는 없다.
- 복잡한 조건이나 엄격한 입력 형식을 통과하기 어려울 수 있다.

대표적인 도구로 AFL++, libFuzzer, Jackalope 등이 있다.

단, 소스코드가 없다는 사실만으로 Black-box Fuzzing이 되는 것은 아니다. Jackalope처럼 바이너리에 계측을 적용하여 실행 경로 피드백을 수집한다면, 소스코드가 없어도 Grey-box Fuzzing을 수행할 수 있다.

### 3.2. 입력 생성 방식에 따른 분류

#### (1) Mutation-based Fuzzing

기존 입력 데이터를 변형하여 새로운 테스트 입력을 생성하는 방식이다.

대표적인 변형 방법은 다음과 같다.

- Bit Flipping: 특정 비트를 반전
- Byte Mutation: 특정 바이트의 값을 변경
- Insertion: 새로운 데이터 삽입
- Deletion: 기존 데이터 삭제
- Splicing: 서로 다른 입력의 일부를 결합

예를 들어 다음과 같은 입력이 있다고 가정하자.

```text
Original : ABCD1234

Mutation 1 : ABXD1234
Mutation 2 : ABCD9999
Mutation 3 : ABCD1234AAAA
```

기존 입력의 일부를 변경하여 다양한 테스트 케이스를 생성한다.

**장점:** 기존 입력을 활용하므로 구현이 비교적 간단하고 다양한 데이터 형식에 적용할 수 있다.

**단점:** 입력 형식이 복잡하거나 엄격한 검증 절차를 거치는 프로그램에서는 변형된 데이터가 초기에 거부될 수 있다.

#### (2) Generation-based Fuzzing

사전에 정의한 입력 형식이나 문법을 기반으로 새로운 테스트 입력을 생성하는 방식이다.

예를 들어 특정 통신 프로토콜의 메시지가 다음과 같은 구조를 가진다고 가정해 보자.

```text
[Header][Length][Command][Payload]
```

Generation-based Fuzzing은 각 필드의 구조와 제약조건을 고려하여 새로운 메시지를 생성할 수 있다.

이 방식은 프로토콜이나 파일 구조를 이해하고 있는 경우에 특히 유용하다.

**장점:** 복잡한 입력 형식을 유지하면서 특정 필드와 조건을 집중적으로 테스트할 수 있다.

**단점:** 입력 문법이나 데이터 구조를 정의하는 작업이 필요하고, 이러한 규칙이 잘못 정의되면 탐색 범위가 제한될 수 있다.

#### (3) Structure-aware Fuzzing

Structure-aware Fuzzing은 입력 데이터의 구조를 이해하고 이를 활용하는 퍼징 방식이다.

예를 들어 JSON 데이터를 처리하는 프로그램에 무작위 바이트만 전달하면 대부분의 입력이 JSON 파싱 단계에서 거부될 수 있다.

반면 JSON의 구조를 유지하면서 값이나 필드 조합을 변형하면 실제 데이터 처리 로직까지 도달할 가능성이 높아진다.

Structure-aware Fuzzing은 Mutation-based 또는 Generation-based 방식과 결합할 수 있으며, 반드시 별개의 입력 생성 방식인 것은 아니다.

### 3.3. Feedback 활용 여부에 따른 분류

| 구분 | Unguided Fuzzing | Feedback-guided Fuzzing |
|---|---|---|
| 입력 생성 | 사전에 정한 규칙이나 무작위 변형 | 실행 결과를 활용한 입력 선택 및 변형 |
| 실행 정보 | 입력 개선에 활용하지 않음 | 커버리지 등 피드백 활용 |
| 장점 | 구현이 단순함 | 유의미한 실행 경로를 탐색하는 데 유리함 |
| 단점 | 같은 경로를 반복할 수 있음 | 계측 및 피드백 수집 비용 발생 |
| 대표 사례 | 단순 랜덤 퍼징 | AFL++, libFuzzer, Honggfuzz |

중요한 점은 Grey-box와 Feedback-guided가 완전히 같은 의미는 아니라는 것이다.

Grey-box는 **얼마나 많은 내부 정보를 활용하는지**를 나타내며, Feedback-guided는 **실행 결과를 다음 입력 생성에 활용하는지**를 나타낸다.

## 4. 주요 Fuzzer 분석

### 4.1. AFL++ (American Fuzzy Lop Plus Plus)

GitHub: https://github.com/AFLplusplus/AFLplusplus

AFL++는 기존 AFL을 기반으로 발전한 커버리지 기반 퍼저로, 다양한 입력을 자동으로 변형하면서 새로운 실행 경로와 오류를 탐색한다.

#### 핵심 특징

**1. Coverage-guided Fuzzing**

AFL++는 프로그램 실행 과정에서 얻은 커버리지 정보를 이용하여 새로운 경로를 발견한 입력을 보존하고 추가로 변형한다.

이를 통해 단순한 무작위 입력 생성보다 효율적으로 새로운 실행 경로를 탐색할 수 있다.

**2. 다양한 실행 및 계측 모드**

AFL++는 여러 방식으로 테스트 대상의 실행 정보를 수집할 수 있다.

- LLVM Mode: 컴파일 과정에서 프로그램에 계측 코드를 삽입
- QEMU Mode: 소스코드가 없는 바이너리의 실행을 계측
- FRIDA Mode: 동적 바이너리 계측을 활용
- Unicorn Mode: CPU 에뮬레이션 기반으로 특정 실행 환경을 테스트

따라서 소스코드를 확보한 프로그램뿐 아니라 바이너리만 존재하는 프로그램에도 적용할 수 있다.

**3. Persistent Mode**

일반적인 퍼징은 각 테스트마다 프로그램을 새로 실행하는 비용이 발생할 수 있다.

Persistent Mode는 하나의 프로세스에서 테스트 대상 코드를 반복 실행함으로써 프로세스 시작에 따른 오버헤드를 줄이는 방법이다.

**4. 다양한 입력 변형 전략**

AFL++는 기본적인 바이트 변형 외에도 비교 연산의 입력값을 탐색하는 CMPLOG, 복잡한 비교를 단순화하는 LAF-Intel 등 다양한 기능을 지원한다.

이러한 기능은 단순한 변형만으로 통과하기 어려운 조건문을 탐색하는 데 도움을 준다.

#### 장점과 한계

**장점**
- 다양한 환경 및 실행 모드 지원
- 코드 커버리지 기반 탐색
- 기존 AFL 생태계 및 다양한 기능 활용 가능
- 소스코드가 없는 바이너리에도 적용 가능

**한계**
- 테스트 환경 및 계측 방식 설정이 필요함
- 복잡한 입력 형식이나 프로그램 상태를 처리하려면 추가 구현이 필요할 수 있음
- 높은 커버리지가 모든 취약점의 발견을 보장하지 않음

AFL++는 범용 소프트웨어를 대상으로 퍼징을 학습하거나 실험할 때 활용하기 좋은 도구라고 생각한다.

### 4.2. Jackalope

GitHub: https://github.com/googleprojectzero/Jackalope

Jackalope는 Google Project Zero에서 공개한 퍼저로, 소스코드가 없는 바이너리를 대상으로 하는 커버리지 기반 퍼징과 사용자 정의 기능에 중점을 두고 있다.

#### 핵심 특징

**1. Binary-oriented Fuzzing**

Jackalope는 소스코드 없이 실행 가능한 바이너리를 테스트하는 환경을 주요 사용 사례로 고려한다.

따라서 소스코드를 확보하기 어려운 소프트웨어를 분석할 때 활용할 수 있다.

**2. TinyInst 기반 계측**

Jackalope는 TinyInst를 활용하여 바이너리 실행을 계측하고 코드 커버리지 정보를 수집한다.

소스코드를 다시 컴파일하지 않아도 실행 정보를 활용한 입력 탐색이 가능하다는 점이 특징이다.

**3. 사용자 정의 기능 지원**

Jackalope는 라이브러리 형태로 활용할 수 있으며 다음과 같은 기능을 사용자가 직접 구현하거나 교체할 수 있도록 설계되었다.

- Custom Mutator
- Custom Sample Delivery
- Custom Instrumentation

이는 테스트 대상의 특성에 맞춰 퍼저를 수정해야 하는 경우 유용하다.

**4. 병렬 실행 지원**

Jackalope는 하나의 시스템 또는 여러 시스템을 활용한 병렬 퍼징을 지원한다.

#### 장점과 한계

**장점**
- 소스코드가 없는 바이너리 분석에 적합
- Windows, macOS, Linux, Android 지원
- 사용자 정의 기능을 추가하기 유리함
- 바이너리 계측을 통한 커버리지 기반 탐색 가능

**한계**
- 대상 프로그램에 맞는 실행 및 입력 전달 환경을 구성해야 함
- 바이너리 계측에 따른 실행 오버헤드가 발생할 수 있음
- 특정 바이너리의 복잡한 상태나 입력 형식을 처리하려면 별도 구현이 필요할 수 있음

처음에는 Jackalope가 단순한 Black-box Fuzzer라고 생각했지만, 실제로는 TinyInst를 통해 바이너리의 실행 정보를 수집하므로 Grey-box Fuzzer에 해당한다는 점이 인상적이었다.

### 4.3. libFuzzer

공식 문서: https://llvm.org/docs/LibFuzzer.html

libFuzzer는 LLVM 프로젝트에서 제공하는 In-process Coverage-guided Fuzzing 엔진이다.

프로그램이나 라이브러리 내부에서 테스트 대상 함수를 반복적으로 호출하며 다양한 입력을 전달한다.

#### 핵심 특징

**1. In-process Fuzzing**

libFuzzer는 퍼저와 테스트 대상 코드가 동일한 프로세스 안에서 실행되는 방식이다.

매번 프로그램을 별도로 실행하지 않고 특정 함수를 반복 호출할 수 있어 테스트 과정의 오버헤드를 줄일 수 있다.

**2. 함수 단위 테스트**

libFuzzer를 사용하려면 일반적으로 다음과 같은 Harness를 작성한다.

```cpp
#include <cstddef>
#include <cstdint>

extern "C" int LLVMFuzzerTestOneInput(
    const uint8_t *Data,
    size_t Size
) {
    // 테스트할 함수에 입력 전달
    return 0;
}
```

이 함수는 퍼저가 생성한 입력 데이터를 전달받는 진입점이다.

실제 테스트에서는 함수 내부에서 분석할 라이브러리의 API를 호출하도록 구현한다.

**3. Sanitizer 연계**

libFuzzer는 AddressSanitizer, UndefinedBehaviorSanitizer 등과 결합하여 메모리 오류와 잘못된 연산을 탐지할 수 있다.

#### 장점과 한계

**장점**
- 함수 및 라이브러리 단위 테스트에 적합
- In-process 방식으로 빠른 반복 실행 가능
- Sanitizer를 활용한 오류 탐지
- C/C++ 프로젝트와 통합하기 편리함

**한계**
- 일반적으로 소스코드 및 테스트 Harness 작성이 필요함
- 프로세스의 전역 상태가 유지되기 때문에 테스트 간 상태 초기화에 주의해야 함
- 전체 응용프로그램보다 개별 API 테스트에 적합한 경우가 많음

참고로 LLVM 공식 문서에 따르면 libFuzzer는 유지보수가 계속되고 있지만, 기존 개발자들은 Centipede라는 다른 퍼징 엔진으로 개발 중심을 옮겼다.

### 4.4. Honggfuzz

GitHub: https://github.com/google/honggfuzz

Honggfuzz는 코드 커버리지 정보를 활용하는 Feedback-driven Fuzzer이다.

소프트웨어 기반 계측과 일부 하드웨어 기반 실행 정보를 활용할 수 있다는 특징이 있다.

#### 핵심 특징

**1. 다양한 Coverage Feedback**

Honggfuzz는 컴파일 과정에서 삽입한 계측 정보뿐 아니라 지원되는 환경에서는 하드웨어 기반 실행 정보도 활용할 수 있다.

**2. Multi-process / Multi-thread 지원**

여러 프로세스와 스레드를 활용하여 퍼징 작업을 병렬로 수행할 수 있다.

**3. Persistent Fuzzing**

반복적인 프로세스 실행 비용을 줄이기 위한 Persistent Fuzzing을 지원한다.

**4. Crash Monitoring**

프로그램 충돌이나 비정상적인 실행 상태를 관찰하여 오류를 발견하도록 지원한다.

#### 장점과 한계

**장점**
- 다양한 커버리지 피드백 방식 지원
- 병렬 실행 가능
- Persistent Mode 지원
- Sanitizer와 함께 활용 가능

**한계**
- 하드웨어 기반 피드백은 운영체제와 하드웨어 지원 여부에 따라 달라짐
- 테스트 대상에 맞는 실행 환경 구성이 필요함
- 입력 구조가 복잡하면 추가적인 입력 변형 전략이 필요할 수 있음

## 5. 주요 Fuzzer 비교

앞서 살펴본 네 가지 퍼저의 특징을 비교하면 다음과 같다.

| 구분 | AFL++ | Jackalope | libFuzzer | Honggfuzz |
|---|---|---|---|---|
| 기본 방식 | Coverage-guided | Coverage-guided | Coverage-guided | Feedback-guided |
| 주요 대상 | 범용 프로그램 | 바이너리 프로그램 | 함수 및 라이브러리 | 범용 프로그램 |
| 소스코드 없이 사용 | 가능 | 가능 | 일반적으로 어려움 | 모드에 따라 가능 |
| 주요 계측 방식 | LLVM, QEMU, FRIDA 등 | TinyInst 등 | LLVM SanitizerCoverage | 소프트웨어 및 하드웨어 피드백 |
| 병렬화 | 지원 | 지원 | 지원 | 지원 |
| 주요 특징 | 다양한 모드와 변형 전략 | 바이너리 분석 및 높은 확장성 | In-process 함수 테스트 | 다양한 실행 피드백 |

이 표를 통해 알 수 있는 것은 모든 퍼저가 동일한 목적과 환경을 위해 만들어진 것은 아니라는 점이다.

AFL++는 다양한 유형의 프로그램과 실행 환경을 지원하는 범용성이 강점이다.

Jackalope는 소스코드가 없는 바이너리를 대상으로 사용자 정의 기능을 적용하는 데 중점을 둔다.

libFuzzer는 특정 함수나 라이브러리를 대상으로 반복적인 In-process 테스트를 수행하는 데 적합하다.

Honggfuzz는 여러 형태의 실행 피드백과 병렬 실행 기능을 제공한다.

따라서 어떤 퍼저가 절대적으로 더 뛰어나다고 판단하기보다는 **테스트 대상의 형태, 소스코드 확보 여부, 실행 환경, 테스트 목표**를 기준으로 적절한 도구를 선택해야 한다.

## 6. Google Fuzzing 자료에서 배운 점

GitHub: https://github.com/google/fuzzing

Google Fuzzing 저장소는 특정 퍼저를 제공하는 프로젝트라기보다 퍼징과 관련된 문서, 튜토리얼, 예제 및 연구 자료를 모아놓은 저장소다.

이 자료를 살펴보면서 퍼징의 효율은 퍼저 자체의 성능뿐 아니라 테스트 대상을 어떻게 구성하는지에도 크게 영향을 받는다는 점을 알 수 있었다.

### 6.1. 좋은 Fuzz Target의 조건

Google의 문서에서는 좋은 Fuzz Target이 갖추어야 할 여러 특성을 설명한다.

대표적으로 다음과 같은 사항이 중요하다.

**첫 번째, 빠르게 실행되어야 한다.**

퍼징은 대량의 입력을 반복적으로 실행하는 작업이므로 한 번의 실행 시간이 길어지면 전체 테스트 효율이 떨어진다.

**두 번째, 동일한 입력에 대해 일관된 동작을 보여야 한다.**

같은 입력을 전달했는데 실행할 때마다 다른 결과가 발생하면, 퍼저가 입력과 커버리지 사이의 관계를 학습하기 어려워진다.

**세 번째, 중요한 기능에 도달할 수 있어야 한다.**

프로그램 시작 부분만 반복해서 테스트한다면 실제 취약점이 존재하는 내부 기능까지 도달하지 못할 수 있다.

**네 번째, 적절한 Seed Corpus를 구성해야 한다.**

서로 다른 실행 경로를 유도하는 대표적인 입력을 제공하면 퍼저가 다양한 기능을 탐색하는 데 도움을 줄 수 있다.

### 6.2. Sanitizer의 중요성

퍼징으로 발견한 모든 오류가 프로그램 충돌로 나타나는 것은 아니다.

예를 들어 배열 범위를 벗어난 메모리 접근이 발생하더라도 프로그램이 즉시 종료되지 않을 수 있다.

이때 AddressSanitizer와 같은 도구를 활용하면 일부 메모리 오류를 더욱 효과적으로 탐지할 수 있다.

따라서 퍼징에서는 입력 생성뿐 아니라 **어떤 오류를 어떻게 관찰하고 판정할 것인지** 역시 중요하다.

### 6.3. Coverage가 높으면 충분할까?

처음에는 퍼징을 통해 코드 커버리지를 높이면 더 많은 취약점을 발견할 수 있다고 생각했다.

그러나 커버리지가 높다는 사실은 프로그램의 많은 코드가 실행되었다는 뜻이지, 모든 입력 조합과 프로그램 상태가 검증되었다는 의미는 아니다.

예를 들어 특정 코드가 실행되었더라도 정수의 최솟값이나 최댓값처럼 특수한 입력을 통해서만 나타나는 오류는 발견하지 못했을 수 있다.

따라서 퍼징 결과를 평가할 때는 커버리지뿐 아니라 발견된 오류의 종류, 재현 가능성, 테스트 입력의 다양성도 함께 고려해야 한다.

## 7. Fuzzing의 실제 활용 과정

AFL++를 이용하여 파일 입력을 처리하는 프로그램을 테스트한다고 가정해 보자.

일반적인 흐름은 다음과 같다.

### Step 1. 테스트 대상 선정

입력 파일을 읽어 처리하는 C 프로그램을 테스트 대상으로 선정한다.

퍼징을 시작하기 전에 프로그램이 어떤 입력을 받으며, 어떤 기능을 수행하는지 파악해야 한다.

### Step 2. 계측 및 빌드

AFL++의 컴파일러를 사용하여 프로그램을 빌드한다.

```bash
afl-clang-fast -g -o parser parser.c
```

위 명령어는 AFL++의 LLVM 기반 계측 모드를 사용하여 프로그램을 컴파일하는 예시다.

`parser.c`는 테스트할 프로그램의 소스코드라고 가정한다.

### Step 3. Seed 준비

```bash
mkdir -p input
printf 'TEST' > input/seed1
```

퍼저가 변형할 초기 입력 파일을 준비한다.

실제 테스트에서는 프로그램이 정상적으로 처리할 수 있는 다양한 입력을 준비하는 것이 좋다.

### Step 4. Fuzzing 실행

```bash
afl-fuzz -i input -o output -- ./parser @@
```

각 옵션은 다음과 같은 의미를 가진다.

- `-i input`: 초기 Seed 디렉터리
- `-o output`: 퍼징 결과 저장 디렉터리
- `--`: 퍼저 옵션과 대상 프로그램 명령어의 구분
- `@@`: AFL++가 생성한 입력 파일의 경로로 치환

이 예시는 `parser`가 첫 번째 명령행 인자로 전달된 파일 경로를 읽도록 구현되었다는 전제에서 사용할 수 있다.

### Step 5. 실행 결과 분석

퍼징을 수행한 후에는 다음 항목들을 확인한다.

- 새롭게 발견된 실행 경로
- 프로그램 충돌 여부
- 실행 시간 초과 여부
- 오류를 발생시킨 입력 파일
- 동일한 오류의 재현 가능성

특히 Crash가 발생했다면 단순히 취약점을 발견했다고 결론 내릴 것이 아니라, 디버깅을 통해 실제 원인을 분석해야 한다.

프로그램의 의도적인 종료, 테스트 Harness의 오류, 실제 메모리 손상 등 다양한 원인이 존재할 수 있기 때문이다.

*위 명령어는 AFL++의 기본 사용 방식을 설명하기 위한 예시이며, 실제 실행 결과를 측정한 실험은 아니다.*

## 8. Fuzzing의 한계와 보완 방법

퍼징은 다양한 버그와 취약점을 자동으로 탐색할 수 있지만 모든 보안 문제를 발견할 수 있는 것은 아니다.

### 8.1. 복잡한 조건문 탐색의 어려움

다음과 같은 코드가 있다고 가정해 보자.

```c
if (a == 12345678 && b == 87654321) {
    // 취약점이 존재할 수 있는 코드
}
```

무작위 입력만으로 두 조건을 동시에 만족시키기는 어려울 수 있다.

이를 보완하기 위해 비교 연산에 대한 피드백, 입력값 추적, Symbolic Execution 등 다양한 방법을 활용할 수 있다.

### 8.2. 복잡한 입력 형식 처리의 어려움

파일 형식이나 네트워크 프로토콜에 엄격한 검증 과정이 존재하면 무작위로 변형한 입력은 초기 단계에서 거부될 가능성이 높다.

따라서 Structure-aware Fuzzing이나 문법 기반 입력 생성 기법이 도움이 될 수 있다.

### 8.3. 상태 기반 프로그램 테스트의 어려움

일부 프로그램은 단일 입력만으로 동작하지 않고 이전 요청이나 내부 상태에 영향을 받는다.

예를 들어 네트워크 프로토콜에서는 다음과 같은 과정이 필요할 수 있다.

```text
연결 요청
    ↓
인증
    ↓
세션 생성
    ↓
데이터 전송
    ↓
세션 종료
```

데이터 전송 단계에 취약점이 존재한다면 먼저 연결과 인증 과정을 통과해야 한다.

이처럼 여러 메시지의 순서와 내부 상태를 고려하는 State-aware Fuzzing이 필요할 수 있다.

### 8.4. 논리적 오류 탐지의 한계

프로그램이 충돌하지 않더라도 보안 문제가 발생할 수 있다.

예를 들어 권한이 없는 사용자의 요청이 정상 처리되거나, 특정 작업이 중복 실행되는 문제가 발생할 수 있다.

이러한 문제는 단순한 Crash 탐지만으로 발견하기 어렵다.

따라서 프로그램이 지켜야 하는 조건을 정의하고 이를 검증하는 Test Oracle을 함께 설계할 필요가 있다.

## 9. 느낀 점 및 앞으로 학습할 방향

이번 미션을 수행하기 전에는 퍼징을 단순히 프로그램에 무작위 데이터를 대량으로 입력해 충돌을 발생시키는 기법이라고 생각했다.

하지만 여러 종류의 퍼징과 퍼저를 살펴보면서 현대적인 퍼징은 무작위 입력 생성에만 의존하는 것이 아니라, 실행 결과와 코드 커버리지를 활용하여 더 유의미한 입력을 탐색하는 방식으로 발전했다는 점을 알게 되었다.

특히 AFL++와 Jackalope를 비교하면서 같은 Coverage-guided Fuzzing에 해당하더라도 테스트 대상과 계측 방식, 사용자 정의 기능에 따라 도구의 특징이 달라진다는 사실이 흥미로웠다.

또한 Google Fuzzing 자료를 살펴보면서 **퍼징의 성능은 퍼저 자체뿐만 아니라 Harness, Seed Corpus, Feedback, Oracle을 어떻게 설계하는지에 따라 달라진다**는 점이 중요하게 느껴졌다.

앞으로는 AFL++를 활용하여 간단한 C 프로그램을 실제로 퍼징해 보고, 입력 변형에 따라 코드 커버리지가 어떻게 변화하는지 확인해 보고 싶다.

이후에는 소스코드가 없는 바이너리 환경에서 Jackalope와 AFL++의 바이너리 계측 방식을 비교하고, 복잡한 입력 구조나 상태를 가진 프로그램에도 퍼징을 적용해 보고자 한다.

최종적으로는 단순히 프로그램 충돌을 발견하는 것을 넘어, 프로그램이 반드시 지켜야 할 조건을 정의하고 이를 자동으로 검증하는 방식까지 학습하고 싶다.

퍼징은 단순한 무작위 입력 테스트가 아니라, **프로그램의 실행 경로를 탐색하고 예상하지 못한 동작을 발견하기 위한 자동화된 보안 검증 기법**이라는 점을 이번 학습을 통해 이해할 수 있었다.
